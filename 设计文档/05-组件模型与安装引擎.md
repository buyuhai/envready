# EnvReady 设计文档 05 —— 组件模型与安装引擎

> 本文档定义"一个组件到底是怎样被装到用户的电脑上的"，以及"怎么判断它真的装好了"。
> 本文档最重要的两条结论写在 5.1 与 5.6，它们分别否掉了参考实现的两个做法。

---

## 5.1 结论一：不安装"需要用户先有编译器"的组件

参考实现为学生提供了 Redis、PostgreSQL、openGauss 等组件的 Linux 安装方式，
其做法是下载**源码包**，然后自动执行 `./configure && make && make install`。

对一个零基础学生来说这是不可接受的：他的机器上通常没有 `make`、`gcc`、`g++`、`readline` 开发头文件，
命令直接失败；而参考实现的做法是"失败只告警、不中断流程"，
于是流程照常往下走、环境变量照常写、进度条照常走完——
用户得到的是一个**看起来装好了、实际上用不了**的环境。

**因此本项目的组件准入规则是：**

> 只收录**开箱即用**的分发形态：官方预编译二进制包、官方安装器、官方包管理产物。
> **任何需要用户机器上存在编译工具链才能安装的组件，一律不收录**，
> 除非该工具链本身是本程序负责安装的组件（例如 C/C++ 环境）。

与之配套的另一条规则：

> 若某组件在官方渠道**只提供源码**（实测：Git for Windows 之外的 Git 在 macOS/Linux 只有源码包、
> 部分数据库只提供源码），则该组件在这些平台上标记为"官方未提供免编译版本"，
> 在界面上说明原因并给出替代建议（系统自带 / 官方安装器 / 官方文档链接），
> **绝不静默下载源码包冒充安装**。

## 5.2 安装方式（`install_kind`）与分支处理

| `install_kind` | 含义 | 典型组件 | 关键处理 |
|---|---|---|---|
| `archive` | 归档包，解压即用 | MinGW-w64、Node、Python、JDK | 校验 → 解压到临时目录 → 校验内容 → 原子改名 |
| `installer` | 官方安装器（需静默参数） | Miniconda、部分数据库 | 校验 → 调静默参数安装到指定目录 → **验证安装目录真的产生了预期文件** |
| `portable` | 单文件可执行/AppImage | 部分 CLI 工具 | 校验 → 放到目标目录 → 赋可执行权限（Unix 0o755） |
| `npm` | 通过 npm 全局安装 | Claude Code 等 AI CLI | 需要先有 Node（依赖建模）；用**我们安装的便携 Node** 执行，避免依赖用户机器上的 npm |
| `noop` | 无需安装，仅做检测/提示 | 系统自带的 Git、已内置的运行时 | 只检测并告知 |

**分支收敛原则**：所有分支最终都汇聚到同一条"后处理流水线"——
`写环境变量 → 自检 → 记录状态 → 呈现人工提示`。
不允许每个分支各自实现一遍后处理（参考实现的单文件里这段逻辑散落在多个方法中）。

## 5.3 归档格式矩阵与识别

| 格式 | 识别依据 | Windows 解压手段 | macOS / Linux 解压手段 |
|---|---|---|---|
| `zip` | 魔术字节 `PK\x03\x04` | 内置 `archive/zip` | 内置 `archive/zip` |
| `tar.gz` / `.tgz` | 魔术字节 `\x1f\x8b` | 内置 `compress/gzip` + `archive/tar` | 同 |
| `tar.xz` | 魔术字节 `\xfd7zXZ` | 内置（需 xz 解码库） | 同 |
| `tar` | 无压缩，靠 tar 头校验 | 内置 `archive/tar` | 同 |
| `7z` | 魔术字节 `7z\xbc\xaf\x27\x1c` | 需要外部工具（见下） | 同上 |
| `rpm` | 魔术字节 `\xed\xab\xee\xdb` | 需自研解析（首期不收录） | 同 |

**三条硬规则：**

1. **格式识别一律以文件头魔术字节为准，不看扩展名。** 实测存在"扩展名是 `.tar`、内容其实是 gzip"
   的真实案例；按扩展名解析会失败，按魔术字节则正确。
2. **macOS 上的程序包必须用 `tar.gz` 而不是 `zip`。** zip 不保留符号链接与 Unix 权限位，
   而 `.app` 目录结构依赖它们，用 zip 打包会导致应用无法运行。
3. **7z 在 Windows 上没有标准库支持**，需要外部工具。本项目采用与参考项目同样的三级降级，
   但**每一级都要先检测再使用，失败要有明确出路**：
   ① Windows 10 1803+ 自带的 `tar.exe`（bsdtar，可解 7z）；
   ② 系统已安装的 7-Zip（探测默认安装路径而不是只看 PATH）；
   ③ 下载官方 `7zr.exe` 到临时目录使用（静态链接的小体积版本）。
   若三级都失败 → 明确告知用户"这个组件需要 7-Zip 才能解压"，并给出选择：
   "自动下载解压工具"（推荐）或"取消本次安装"。**不允许静默失败。**

## 5.4 通用安装流水线（8 步）

```
步骤 1  准入检查
        磁盘空间（需求 × 1.5）、目标目录可写、依赖是否满足、是否与已装组件冲突
        —— 全部在"开始之前"完成，绝不在下载到一半才报错

步骤 2  下载
        见 06-下载引擎；产出 <APP_ROOT>/downloads/<file>.part → 校验 → 改名

步骤 3  完整性校验
        SHA-256 与清单比对；不符则删除文件、记 error、按错误分类决定重试

步骤 4  解压到暂存区
        <ENV_ROOT>/<组件key>/.stage-<版本>/（隐藏目录，与其他版本隔离）
        解压过程输出进度（大包解压可能数十秒，必须有反馈）

步骤 5  内容校验
        解压后检查"预期文件清单"是否存在（例如 gcc 版本必须有 bin/gcc.exe 或 bin/gcc）
        任一关键文件缺失 → 整批作废、删除 stage 目录，报"安装包内容异常"

步骤 6  原子落盘
        .stage-<版本> → 改名为 <组件key>-<版本>/
        改名是同一文件系统内的原子操作；名字冲突（同版本重装）时先改名旧的为 .bak 再替换

步骤 7  配置环境变量
        见 07-环境变量管理；写前备份，幂等，写后回读校验

步骤 8  自检 + 呈现
        实际运行 verify 命令 → 解析版本 → 与清单比对 → 记录组件状态
        展示 post_notes（人工操作提示）到界面上
```

**为什么步骤 4 用隐藏的 `.stage-` 目录而不是直接解压到最终目录：**
`<ENV_ROOT>/<组件key>/` 下如果有多个目录，界面上"我们检测到你有 3 个 Python"会让学生困惑；
用点开头的暂存目录可以让检测逻辑简单地把"未完成的安装"排除在外（同时它也是崩溃恢复的抓手）。

## 5.5 内容校验的"预期文件清单"

清单里每个版本的 `platforms.<平台>` 都应（由工具链自动生成）包含
`expect_files`：安装成功后必然存在的相对路径列表，例如：

- MinGW：`bin/gcc.exe`（Windows）/ `bin/gcc`（Unix）、`bin/g++`、`bin/gdb`
- Python：`python.exe` / `bin/python3`
- JDK：`bin/java.exe` / `bin/javac`

这条字段的价值：**区分"解压成功"与"解压出了正确的东西"**。
压缩包被截断、被掉包、或解压工具静默跳过部分文件时，只有这张清单能发现。

## 5.6 结论二：进度条走完 ≠ 安装成功（自检）

参考实现把"下载完成 + 解压完成"等同于安装成功（日志打一句"安装完成"），
用户唯一的成功凭据是进度条到 100%。本项目要求：

**每个组件都必须有 `verify` 定义，且安装流程必须实际执行它。**

| 项 | 要求 |
|---|---|
| 执行内容 | `verify.command` + `verify.args`（例如 `gcc --version`），必要时可指定 `cwd` |
| 判定 | 退出码等于 `expect_exit`，且 `parse` 正则能从输出中取出一个版本号 |
| 版本比对 | 取出的版本与清单中该版本的期望区间比对；不一致时**不判定为失败**，但标记为"版本与预期不符"并提示用户 |
| 超时 | 默认 10 秒；超时视为失败（可能是动态库缺失导致挂起） |
| 失败处理 | **安装不标记为成功**，界面显示"已安装，但自检未通过"，并给出下一步：查看详情 / 重新安装 / 手动排查提示 |
| 呈现 | 成功时展示"验证通过：gcc (MinGW-W64 ...) 14.2.0"，让用户看到真实输出的一行 |

`verify` 必须在**新开的环境上下文中**执行（即把将要写入的环境变量先注入子进程环境），
否则会出现"自检时用的是临时拼出来的 PATH，用户新开终端却不是这样"的错位。

## 5.7 组件状态模型

界面上每个组件只有 4 种状态，每个状态对应一句人话和一个下一步动作：

| 状态 | 判定依据 | 界面文案 | 可用动作 |
|---|---|---|---|
| 未安装 | 目录不存在且环境变量未指向它 | "还没装" | 安装 |
| 已安装可用 | 目录存在 + 自检通过 | "已装好（14.2.0）" | 打开文件夹 / 重新验证 / 卸载 |
| 已安装待验证 | 目录存在但从未自检（例如用户手工拷进来的） | "检测到你已装过（未验证）" | 验证 / 使用 / 忽略 |
| 有问题 | 目录存在但自检失败，或环境变量指向不存在的路径 | "装好了但好像不能用" | 修复 / 查看详情 / 重新安装 |

**第四种状态是参考实现完全缺失的**：它的检测只看"目录是否存在"，
于是"配置环境变量失败"这种最严重的情况在界面上仍显示为已下载状态，
用户以为成功了。

## 5.8 多版本共存与目录命名

```
<ENV_ROOT>/<组件key>/
├── .stage-<版本>/            安装中的暂存（正常情况下一闪而过）
├── <组件key>-<版本>/          已安装的版本，可同时存在多个
│   └── bin/ ...
└── <组件key>-<版本>.bak/      被替换掉的旧目录（短暂存在）
```

- 目录名规则与参考实现保持一致（`<key>-<version>`），便于我们对照与迁移。
- `version` 使用清单中的**逻辑标识**，不随官方文件名变化（见 `04` 的说明）。
- 同一组件多版本共存是允许且被鼓励的（学生可能同时需要 JDK 8 和 JDK 21），
  但**同一时刻只有一个版本被环境变量"激活"**——这一层由 `07-环境变量管理` 负责。

## 5.9 依赖处理

| 情形 | 处理 |
|---|---|
| 硬依赖（A 必须有 B 才能工作） | `requires` 字段声明；安装 A 前检查 B，缺失则提示"这个还需要先装 Node，要一起装吗？"并支持一键连带安装 |
| 软依赖（有更好，没有也能用） | `suggests` 字段；只在结果页提示 |
| 循环依赖 | 清单生成阶段由工具链检测并报错，不允许发布 |
| 依赖已由系统提供 | 检测到即跳过（例如 macOS 自带 Git），并说明"系统已自带，无需安装" |

参考实现完全没有依赖建模：Claude Code 需要先装 Node，这件事只写在 README 里，
界面上一句提示都没有，学生装完发现命令不存在。

## 5.10 各组件的接入优先级（首期范围）

**首期只承诺"不少于 5 类环境跑通且成功率 ≥ 90%"**，因此按下面顺序接入，
每一类都必须满足 5.1 的准入规则：

| 优先级 | 环境 | 组成 | 理由 |
|---|---|---|---|
| P0 | **C / C++** | MinGW-w64（Windows）、系统 clang/gcc 检测（macOS/Linux）+ VS Code 配置生成 | 项目明确要求，且已有前期成果可直接迁移（见 `09`） |
| P0 | **Python** | 官方 Python（Windows 用官方安装器或 embeddable + get-pip；Unix 用官方包） | 入门第一语言 |
| P0 | **Java** | Temurin（Adoptium）JDK | 课程需求最大 |
| P1 | **Node.js** | 官方 Node（附带 npm） | 前端与大量 CLI 工具的基础 |
| P1 | **代码编辑器** | VS Code（若未安装则引导安装；**不代替用户装系统级包管理器**） | 学生需要一个写代码的地方 |
| P2 | 常用工具 | Git（仅 Windows 官方 MinGit；Unix 提示系统自带） | 工具链补全 |
| P3 | 其他语言 | Go / Rust 等 | 后续按需求接入 |

**明确不在首期范围**：数据库（MySQL/PostgreSQL/达梦/openGauss 等）、大数据全家桶
（Hadoop/Hive/HBase/Spark/Flink/Kafka）、AI 命令行工具。
原因：它们要么体积巨大（实测单包最高 1.8 GB）、要么需要初始化与建库等人工步骤、
要么需要用户有相当基础，与"零基础学生第一次装环境"这个场景不匹配。
它们属于后续版本的目标（清单格式已为它们留好字段）。
