# EnvReady 设计文档 09 —— C / C++（MinGW）接入

> 项目要求：除参考实现已包含的语言外，**新增 C/C++ 的环境配置**，
> 可参考前期自研的 MinGW 自动安装脚本，但要**兼容进整个程序**。
> 前期成果位置：`D:\work place\vscode c deployment environment\`，
> 核心脚本 `Install-MinGW.ps1`（58,508 字节，44 个函数），还原脚本 `Restore-UserPath.ps1`。
> 本文档定义"已有能力如何迁移进 Go 版 EnvReady"，以及 C/C++ 组件的完整行为规格。

---

## 9.1 为什么 C/C++ 是首期重点

1. 它是**项目明确要求**的新增能力。
2. 它是**最容易失败**的一类环境：编译器不在 PATH 里、头文件找不到、
   编辑器没有配置编译任务，学生看到的是英文报错，几乎无法自行解决。
3. 我们**已经有可运行的实现**（PowerShell 版），迁移风险最低，可以作为整个 Go 架构的第一个验证对象。

因此 C/C++ 组件不只是"多一个组件"，而是**整条流水线的样板间**：
它跑通了，其他语言只是换清单数据。

## 9.3 MinGW-w64 的发行选择

| 可选发行 | 优点 | 缺点 | 决定 |
|---|---|---|---|
| **winlibs（GCC 14.x / 13.x）** | 版本新、构建规范、单独提供 UCRT 与 MSVCRT 两套、同时提供 `.zip` 与 `.7z` | 体积较大 | **推荐** |
| mingw-builds | 老牌、资料多 | 实测其默认（自动选择）包仍停留在 2018 年的 GCC 8.1.0，对新手是隐形陷阱 | 备用（仅在清单明确指定新版本时使用） |
| MSYS2 | 生态完整、有包管理器 | 对新手复杂，安装与更新需要命令行操作 | 不使用 |
| LLVM/Clang + MinGW | 有优势 | Windows 上配置更复杂 | 不使用 |

**关于两套运行库的选择**（需要在清单里为每个版本明确标注）：

| 变体 | 说明 | 建议 |
|---|---|---|
| UCRT | 使用 Windows 10+ 自带的通用 C 运行库 | **首期推荐**（体积小、Win10 及以上都支持） |
| MSVCRT | 兼容老系统（Win7/8） | 仅在用户需要支持老系统时提供 |

**关于线程模型**：`posix` 与 `win32` 两种。学生若要写多线程（`std::thread`）需要 `posix`；
但 `posix` 变体在标准库行为上有个别差异。**首期推荐 `posix` + `seh`（64 位）**，
因为它对 C++ 标准库特性支持最完整，也是大多数教程默认使用的组合。

**关于压缩包格式**：winlibs 同时提供 `.zip` 与 `.7z`。
**优先选 `.zip`**，因为它不需要任何外部工具就能解压（不触发 7-Zip 三级降级路径），
减少一个失败面。只有在 zip 版本不可用或体积差异极大时才用 `.7z`。

## 9.4 安装规格

| 项 | 规格 |
|---|---|
| 安装位置 | `<ENV_ROOT>/mingw/mingw-<版本>/` |
| 解压后目录结构 | 根下直接是 `bin/`、`include/`、`lib/`、`x86_64-w64-mingw32/` 等（`strip_root` 视包而定，由清单指定） |
| 需要的子目录 | `bin` |
| 环境变量 | **只加 PATH，不设自造的 `XXX_HOME`** |
| 验证命令 | `gcc --version`、`g++ --version`、`gdb --version`、`mingw32-make --version` |
| 判定标准 | 四条命令全部返回退出码 0；`gcc` 与 `g++` 必须成功，`gdb` 与 `mingw32-make` 失败时降级为"警告"而不是失败（有些构建不含 gdb） |

### 关于"不设自造环境变量"的说明

参考实现里有"写入大量自造环境变量名"的问题：官方并不认识这些变量，
它们唯一的作用是给工具自己用来检测，却永久留在用户的注册表里。

**MinGW 是这条规则的典型案例**：GCC 靠 PATH 工作，不存在官方的 `MINGW_HOME`。
因此本项目的规则是：

> 只有当**上游官方文档明确要求**某个环境变量时，我们才设置它；
> 我们自己的检测信息一律存在自己的记录文件里（`<ENV_ROOT>/.active.json` 与 `<APP_ROOT>/managed.json`），
> **不污染用户的系统环境变量**。

## 9.5 编辑器配置自动生成（本项目相对参考实现的核心增量）

**问题**：即使 `gcc` 装好了，学生在 VS Code 里写 C 语言仍然跑不起来——
按下运行键没反应，或者提示找不到编译器。原因是编辑器需要知道"用哪个编译器、怎么编译、
编译出来放哪、怎么调试"，而这需要 `.vscode/` 下三个配置文件。

**因此 C/C++ 组件的交付物不只是编译器，还包括一份可直接使用的编辑器配置。**

### 9.5.1 生成的四个文件与各自职责

| 文件 | 作用（对学生的一句话解释） | 关键内容 |
|---|---|---|
| `.vscode/tasks.json` | "按哪个按钮来编译" | 一条编译任务，调用我们装好的 `gcc`，输出到 `build/` |
| `.vscode/launch.json` | "按哪个按钮来运行/调试" | 关联编译任务，配置 `gdb` 调试器路径（来自我们装的 `gdb`） |
| `.vscode/c_cpp_properties.json` | "让编辑器认识这些头文件" | `includePath` 指向我们装的 `include` 与 `x86_64-w64-mingw32/include` |
| `.vscode/settings.json` | "一些便利设置" | 保存时自动格式化、文件编码 UTF-8、终端编码（避免中文乱码） |

**所有路径必须指向实际安装位置**（从 `.active.json` 读取），并且**使用绝对路径**——
用相对路径或依赖环境变量继承是学生踩坑的主要来源（从 Dock/开始菜单启动的编辑器
可能拿不到新写入的 PATH）。

### 9.5.2 生成时机与位置

| 场景 | 行为 |
|---|---|
| 用户选择"帮我准备一个练习项目" | 创建一个示例文件夹（含 `hello.c`、`.vscode/` 四文件、`README.txt`），并打开说明 |
| 用户已有自己的代码文件夹 | 在"接下来做什么"页面提供"为这个文件夹生成配置"，让用户选择文件夹后生成 |
| 生成到已有 `.vscode/` 的文件夹 | **先检测是否已存在同名文件**：存在则备份为 `.bak` 再写，并在结果页说明"已备份原配置" |

### 9.5.3 生成的示例程序

首期提供一个最小可运行示例：

- `hello.c`（C 语言版本）与 `hello.cpp`（C++ 版本）各一份，内容是带中文注释的 Hello World，
  并在 README 里说明"中文注释不影响编译，但如果看到乱码，说明终端编码需要调整"。
- 附带一句"改了代码之后，按 <kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>B</kbd> 编译，
  按 <kbd>F5</kbd> 运行/调试"——把快捷键写下来，学生不用去查文档。

### 9.5.4 中文字符串与编码（必须处理）

Windows 上最容易让学生崩溃的问题之一：程序里写中文，控制台输出乱码。因此：

- `settings.json` 中固定文件编码为 UTF-8。
- 示例程序里给出一行"如果出现乱码，在代码开头加这句"的注释提示。
- 结果页里用一句话解释："Windows 的命令行默认不是 UTF-8，所以中文可能显示成乱码。
  这不影响程序的逻辑。"

## 9.6 macOS / Linux 的处理

这两个平台通常**已经自带或可以一行安装**编译器，我们不做 sudo 操作（红线：不尝试绕过权限）。

| 平台 | 检测 | 若缺失 |
|---|---|---|
| macOS | `xcrun --find clang` 或检测 `/Library/Developer/CommandLineTools` | 明确告知："需要安装苹果的开发者命令行工具。安装时系统会弹出一个窗口，点击'安装'即可（不需要付费账号）。" 并提供"打开安装"按钮（触发系统安装）与验证命令 |
| Linux | `gcc --version` / `cc --version` | 告知对应发行版的安装命令（apt/dnf/pacman），**复制按钮给命令，但由用户自己执行**（因为需要 sudo） |

**Linux/macOS 上的 VS Code 配置生成同样提供**（用系统 `gcc`/`clang` 的绝对路径）。

**重要原则**：需要 sudo 的动作一律不由程序代做，只给命令与说明。
这既是安全要求，也避免"程序要了我的密码"这种信任破坏。

## 9.7 常见问题与自愈（结果页与帮助页共用）

| 现象 | 原因 | 我们的提示 |
|---|---|---|
| `gcc` 不是内部或外部命令 | 环境变量写了但当前窗口未重启 | "请重新打开一个命令行窗口（已经打开的窗口不会更新设置）" |
| 编辑器里编译报错找不到 `gcc` | 编辑器启动早于配置生效，或配置未生成 | 提供"重新生成编辑器配置"入口（我们的配置用绝对路径，本可不依赖环境变量） |
| `#include <stdio.h>` 报找不到 | 解压不完整或 `c_cpp_properties.json` 路径不对 | 提供"重新验证安装"入口（重跑自检并检查 `expect_files`） |
| 中文乱码 | Windows 控制台编码 | 见 9.5.4 |
| 杀软报警删除 `gcc.exe` | 编译器的可执行文件常被杀软误判 | "有些安全软件会误删编译器的文件。如果某个命令突然不能用了，请重新验证安装。" |
| `undefined reference` | 链接参数问题（学生代码问题） | 不属于本程序范围，但帮助页给一条排查建议 |

## 9.8 验收标准（C/C++ 组件的 SPEC）

必须能通过以下全部检查，才认为"这个组件做完了"：

1. 在一个**从未装过任何开发工具**的 Windows 机器上，双击安装后：
   - 新开命令行窗口，`gcc --version` 输出含版本号；
   - `g++ --version`、`gdb --version`、`mingw32-make --version` 输出正常（`gdb` 允许降级为警告）。
2. 用生成的示例项目，在 VS Code 里 <kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>B</kbd> 能编译，
   <kbd>F5</kbd> 能进入调试并在断点处停下。
3. 界面上显示的版本号与命令行输出的一致。
4. 卸载/切换版本后，PATH 中**不残留**旧版本的条目（用脚本断言 PATH 内容）。
5. 断电注入测试（在解压中途杀进程）后，重新启动程序能正常完成或安全放弃，
   且环境中**没有**半成品条目。
6. 一键还原能把用户 PATH 恢复到安装前的状态（逐字节比对备份）。
7. 全程**不需要管理员权限**，不出现 UAC 弹窗（首期硬性要求）。
