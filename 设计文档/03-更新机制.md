# EnvReady 设计文档 03 —— 更新机制

> 更新机制是本项目的显式需求，也是相对参考实现 murig 的关键增量（它完全没有自更新，
> 用户必须自己去 GitHub 下载新包）。
> 目录与指针的定义见 `02-目录布局与状态机.md`，本文档只讲"更新怎么发生、失败怎么办"。

---

## 3.1 为什么需要启动器：第一性原理

**正在运行的程序无法原子替换自身。**

- Windows：运行中的 `.exe` 被文件锁占用，无法被覆写。
- macOS / Linux：可以 `unlink` 正在运行的文件，但当前进程仍指向旧 inode，
  替换只对"下次启动"生效——所以本质上还是需要一次重启，且中途失败没有退路。

由此推出三种可行做法：

| 做法 | 说明 | 取舍 |
|---|---|---|
| 外部更新器进程 | 主程序下载好更新器，退出，由更新器替换主程序 | 可行，但多一个进程要维护，且更新器自身怎么更新没解决 |
| 自我改名再覆盖 | 运行中的 exe 改名，把新版放到原名，重启 | **否决**：Windows 上失败率高，且杀软对"程序改自己名字"高度敏感（误报） |
| **启动器 + 版本目录 + 指针** | 更新退化为"改一个指针文件" | **采用**：天然原子、天然可回滚、不碰运行中的文件、支持多版本共存 |

启动器只有几百 KB 到 2 MB 的职责：读指针、起进程、必要时观察与回退。它几乎不变，
因此它自身的更新频率极低（见 3.6）。

## 3.2 三个层次的更新必须分开

这是从参考实现学到的教训：它把 29 个组件硬编码在 `build_components()` 里，
新增一个组件必须改代码、重新打包、重新发版。我们必须把"数据"和"程序"分开。

| 层次 | 更新内容 | 频率 | 是否需要重启 | 谁触发 |
|---|---|---|---|---|
| **资源清单** | 组件列表、版本、下载地址、校验和 | 高（上游一发版就变） | **不需要**，下次打开组件列表即生效 | 启动后自动（24h 一次） |
| **主程序** | 界面、安装逻辑 | 中（有缺陷或新功能时） | 需要（提示重启） | 启动后自动检查，用户确认 |
| **启动器** | 指针处理、健康检查逻辑 | 极低 | 下次启动生效（由主程序顺手替换） | 随主程序一起 |

**由此得到两条设计铁律：**

1. **能用清单解决的，绝不改程序。** 新增一个语言环境 = 改一份 JSON，不需要发版。
2. **程序更新绝不打断正在进行的任务。** 下载、安装、自检过程中不提示更新；
   更新包可以后台静默下载与校验，等任务结束再提示。

## 3.3 主程序更新流程

```
① 检查（启动后延迟 5 秒，且每 24 小时最多一次）
   拉取 client.json（静态托管清单，不走 GitHub API —— 见 3.8）
   比较 latest 与自身版本
   ├─ latest <= 自身 → 结束
   └─ latest >  自身 → 继续

② 后台准备（不打扰用户，不显示进度条，只在"关于/更新"页留状态）
   选平台对应的包 → 多镜像测速 → 下载到 downloads/<file>.part → 校验 SHA-256
   ├─ 失败 → 静默重试一次；再失败则放弃本次更新（记日志，不打扰用户）
   └─ 成功 → 解压到 app/<新版本>.tmp-<随机> → 逐个文件校验 → 原子改名为 app/<新版本>/
                （此时新版已就位，但还没有启用）

③ 提示用户（仅在"当前无任务"时）
   "有新版本 1.1.1。现在重启使用新版本？" [现在重启] [稍后]
   ├─ 稍后 → 记录"待启用"，下次启动自动启用（不重复询问）
   └─ 现在 → 进入 ④

④ 切换指针（写 current.json：version=新版本, state=pending, prev=旧版本, attempts=0）
   然后退出自身 → 由启动器拉起新版 → 启动健康检查（3.4）

⑤ 健康检查通过 → state=stable，清理旧版本（GC）
   健康检查失败 → 回退到 prev，并在下次启动时用人话告知用户
```

**关于"现在重启"的实现细节**：由于 App 自身无法拉起新版本（它就是要被替换的那个），
它只需**退出**，由启动器完成启动。因此"现在重启"在界面上应表述为"正在重启…"，
实际动作是：写指针 → 让启动器知道自己要重启（例如启动器以 `--restart-after` 方式驻留，
或直接退出并由用户点击图标；具体实现见 3.5 的"重启传递"）。

## 3.4 启动健康检查（防变砖机制）

**只对刚更新的版本执行**（`state=pending`）。日常启动（`stable`）不做任何额外等待。

### 3.4.1 凭据传递：文件 + nonce

| 机制 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 子进程退出码 | 最简单 | 只能发现"启动即崩"，发现不了"窗口白屏" | 不用 |
| 管道 / stdout | 实时、无需落盘 | 启动器退出后管道断开；Windows 跨进程句柄传递麻烦 | 不用 |
| **文件 + nonce** | 跨平台简单、可异步写、天然留证供诊断 | 需处理陈旧标记（用 nonce 解决） | **采用** |

协议：

1. 启动器生成随机 `nonce`，写入 `app/<新版本>/.handshake`
   （内容：nonce、启动器 PID、时间戳）。这个文件同时是诊断线索：
   如果它存在而健康标记不存在，说明"启动器起过进程但主程序没报告成功"。
2. 启动器以环境变量 `ENVREADY_HANDSHAKE=<nonce>` 启动主程序。
3. 主程序把 nonce **回写**进健康标记文件。
4. 启动器校验健康标记里的 nonce 与自己生成的一致 —— **防止把上一轮残留的标记当成本次成功**。

### 3.4.2 两阶段标记

| 阶段 | 写入时机 | 证明什么 |
|---|---|---|
| stage 1 | Go 侧应用启动完成（WebView 初始化成功） | 进程活着、运行时与 WebView 可用 |
| stage 2 | 前端页面 DOM ready 后回调 Go | 前端资源加载并执行成功 |

**判定成功只认 stage 2。** 两阶段分开记录的价值在诊断：
stage 1 出现而 stage 2 超时 → 直接定位为"前端加载失败"，而不是笼统的"启动失败"。
这类信息会写进日志与用户可选提交的诊断包。

### 3.4.3 判定与重试

| 情况 | 判定 | 动作 |
|---|---|---|
| 子进程退出码非 0，或启动后 < 2 秒即退出 | 立即失败 | 不用等满超时，直接进入重试/回退判定 |
| stage 2 出现且 nonce 匹配 | 成功 | 指针置 `stable`，清空 `attempts` 与标记文件 |
| 进程活着但超时（默认 30 秒） | 记为一次失败尝试 | 结束该进程；若 `attempts < 2` 则 `attempts+1` 后再试一次（冷启动/杀软扫描可能很慢）；达上限才回退 |
| 已经重试过仍失败 | 回退 | 见 3.4.4 |

**超时值 30 秒是暂定值，必须在最差的机房机器上实测校准**（WebView2 冷启动 + 杀软全盘扫描）。
理由：只在刚更新后发生一次，用户等待可接受；宁可多等 10 秒，也不要误判回退。

### 3.4.4 回退动作（必须幂等）

1. 写指针：`{version: prev, state: stable, attempts: 0}`。
2. 把失败版本目录改名 `app/<新版本>.broken-<时间戳>`（**不删除**，保留现场供诊断）。
3. 结束所有相关子进程。
4. 写日志：失败阶段、子进程退出码、stdout/stderr 摘要、耗时。
5. **下次启动时用人话告知用户**：
   "上次更新到 1.1.1 后程序没能正常启动，已经自动回到 1.1.0，你可以继续使用。
    这个问题我们已经记录下来。" [查看详情] → 打开日志目录 / [复制诊断信息]

第 2 步"不删除"是刻意的：删掉就永远无法诊断；保留几十 MB 的代价远小于"用户报了个问题我们查不了"。

### 3.4.5 特殊情形

- `prev` 缺失（首次安装即失败）→ 无法回退，进入修复模式（见 `02` 的 2.6）。
- `prev` 指向的版本目录已被 GC 清掉 → 优先回退到"app 下任意校验通过的版本"，
  其次进入修复模式。
- 回退后仍启动失败 → 连续失败计数，达到 3 次则停止自动重试，
  显示"程序无法启动，请重新下载完整安装包"，并给出下载入口（避免无限重启循环）。

## 3.5 重启传递与不打断任务

**问题**：主程序写指针后自己退出，谁来启动新版？
**方案**：主程序在写指针前，先确保"重启接力"存在，二选一：
  (a) 启动器以 `--wait-exit <pid>` 模式驻留等主程序退出后立即启动新版（用户无感）；
  (b) 主程序退出后由用户点击图标（更简单，但体验上"点了更新却什么都没发生"容易困惑）。

**采用 (a)**，因为"点了更新就自动回来"是学生最容易理解的交互；实现代价只是启动器多驻留几秒。
注意 (a) 与"启动器不常驻"并不矛盾：**不常驻是默认行为，驻留是有明确理由的例外**
（等待重启接力、或处于 `pending` 观察期）。

**绝不打断任务**：以下状态中一律不提示更新，也不写指针切换：
- 有下载/安装/自检任务进行中
- 有组件加载/版本切换操作进行中
- 用户正在确认某个对话框

更新包可以在后台准备好（下载、校验、解压、就位），**唯一被推迟的是"写指针"这一步**。

## 3.6 启动器自身的更新

启动器极少变，因此采用"顺手替换"策略，不做单独的更新通道：

1. 程序包里同时包含新版启动器（`EnvReady.exe`）。
2. 主程序在启动成功、且确认**启动器当前没有运行**（不可能同时运行，因为启动器已退出）
   的情况下：把新启动器写为 `EnvReady.exe.new`，校验其哈希。
3. **下一次启动**由旧启动器完成：旧启动器启动时若发现 `EnvReady.exe.new` 且校验通过 →
   把自身改名或直接删除，再把 `.new` 改名为 `EnvReady.exe`，记日志。
   （Windows 上自己改名自己是允许的，因为不涉及覆盖运行中的文件。）
4. 若替换失败 → 保留 `.new`，下次再试；连续失败则不再尝试并记 `warn`。

**注意**：这一机制只在"旧启动器能正常启动"的前提下工作。因此启动器代码应尽量冻结、
尽量简单——它越简单，越不容易需要更新，整个链条越稳。

## 3.7 用户可见行为规范

| 事件 | 呈现方式 | 理由 |
|---|---|---|
| 有新版本可供更新 | 标题栏/关于页一个不显眼的标记；不弹窗 | 学生开程序是为了写代码，不是为了更新 |
| 更新包已下载就位 | "新版本已准备好，下次打开自动使用" | 让用户知道"不用管它" |
| 需要重启且当前无任务 | 询问"现在重启 / 稍后"，"稍后"要说明下次自动生效 | 不打断、不隐瞒 |
| 更新失败（下载/校验） | **默认静默**，只在"关于/更新"页留一条记录 | 失败的技术原因对用户无意义，反复提示只会造成恐慌 |
| 回退发生 | **必须明确告知** + 查看详情 | 这是"程序行为与用户预期不同"的情况，必须解释 |
| 强制更新（低于 min_supported） | 明确说明原因（安全修复），提供更新入口 | 极少发生，但发生时用户有知情权 |

## 3.8 版本清单的获取方式（为什么不走 GitHub API）

**结论：清单放在静态托管上，用普通 HTTPS GET 获取，不走 GitHub Releases API。**

原因（来自真实场景推断）：

1. GitHub API 未认证时限流为每小时 60 次，**按 IP 计**。高校宿舍/机房的 NAT 出口是全校共用一个 IP，
   学生装机高峰时必然 403。参考实现的实测中，抓取 `git-for-windows` 的 release 列表单次响应体
   就有 1.4 MB、耗时超过 100 秒，同样印证了这条路在国内校园网络下不可靠。
2. 静态 JSON 可以放 CDN（jsDelivr 等）与多个镜像，天然获得"多镜像测速"能力。
3. 静态 JSON 可以签名（见 `11-安全与信任模型.md`），而 API 响应无法承受额外封装。

因此：`client.json` 与组件清单都是**静态文件**，由 CI 生成并发布，
客户端从多镜像择优拉取（见 `04-资源清单规范.md` 与 `06-下载引擎.md`）。

## 3.9 为什么不用现成的自更新库

调研过的常见方案（go-selfupdate / minio-selfupdate 等）多为
"重命名自身 → 覆盖 → 重启"模式，**不覆盖我们需要的**：

- 版本目录化与原子指针切换
- 启动健康检查与自动回退
- 用户可写目录下的更新（无管理员权限）
- 与"清单更新"分离（它们通常只更新二进制）
- 用户可见的解释性文案

**可以借鉴的是其中的"原子替换工具函数"**（例如 Windows 上 `MoveFileEx` 的替换语义、
Unix 上 `rename` 语义），这些可以自己实现，代码量很小。

**架构上的额外收益**：程序自身更新可以复用给学生用的下载引擎
（断点续传、哈希校验、多镜像测速、代理支持）——自更新是这个引擎的第一个使用者，
等于给引擎做了一次真实测试。

## 3.10 更新机制的测试矩阵

无需真的发版即可测试（本地起一个 HTTP 服务 + 伪造版本号）：

| # | 场景 | 期望 |
|---|---|---|
| 1 | 正常更新（下载 → 校验 → 解压 → 切换 → 启动成功） | 新版可用，旧版保留 |
| 2 | 下载中断（杀进程）后重启 | 续传成功（或安全地全量重下） |
| 3 | 包被篡改（哈希不符） | 拒绝安装，删除文件，旧版继续可用 |
| 4 | 解压中被杀 | 残留 `.tmp-*` 被清理，旧版继续可用 |
| 5 | 新版主程序故意损坏（启动即崩） | 自动回退到旧版，并告知用户 |
| 6 | 新版能启动但前端不 ready（只写 stage 1） | 超时后回退，日志能区分"前端失败" |
| 7 | 新版启动很慢（故意等 25 秒才写 stage 2） | 视为成功，不回退（验证超时值是否合理） |
| 8 | `current.json` 被手工改坏 | 进入修复模式，选到可用版本 |
| 9 | 当前版本目录被删 | 进入修复模式 |
| 10 | 磁盘写满 | 在"开始之前"或"失败时"给出明确提示，不产生半成品 |
| 11 | 更新过程中关机（断电模拟） | 指针未变或变为 pending，两种都能自愈 |
| 12 | 有安装任务进行中时到达更新 | 不提示、不切换，任务完成后才提示 |
