# EnvReady 设计文档 01 —— 工程结构与代码 / 注释规范

> 本文档对应项目硬约束："代码不能混乱，可以分步来写，同时批注是关于什么的功能，方便后续维护。"
> 规范的目的是让**半年后的我们自己**能直接看懂任何一段代码在干什么。

---

## 1.1 仓库顶层布局

```
EnvReady/                       ← 项目根，同时是 Git 仓库根
├── cmd/
│   ├── envready/               启动器入口（产物名 EnvReady，体积极小）
│   └── envready-gui/           主程序入口（Wails 应用）
├── internal/                   业务代码（按职责分包，见 1.2）
├── frontend/                   Wails 前端（HTML/CSS/JS，引导式界面）
├── assets/                     图标、字体、内置清单快照
├── tools/                      清单抓取 / 巡检 / 打包脚本（不参与主程序编译）
├── 设计文档/                   本套设计文档
├── 思路收集.txt                讨论过程的想法记录
└── .github/workflows/          CI：构建、测试、巡检、发布
```

**两条硬规则：**

1. **`cmd/` 里的 `main.go` 只能做装配**（读参数、初始化、调 `internal/app`、处理退出码），
   不允许出现业务逻辑。这样启动器和主程序可以复用同一套 `internal`，后续拆分也不会失控。
2. **启动器与主程序是两个独立可执行文件**，二者都不允许 import 对方。它们之间只通过
   **指针文件 + 命令行参数 + 退出码**通信，不通过共享内存或彼此的函数调用
   （因为它们必然有一方在运行时另一方正在被替换）。

## 1.2 `internal` 分包职责

一个包只负责一件事。包名即职责，看到 import 就知道这行代码在动什么。

| 包 | 职责 | 不允许做的事 |
|---|---|---|
| `internal/app` | 应用装配：把各模块连起来，生命周期与关停顺序 | 不写具体业务规则 |
| `internal/paths` | APP_ROOT / ENV_ROOT 解析，三平台路径规则 | 不创建目录（只算路径） |
| `internal/update` | 自更新：指针读写、状态机、健康检查、启动器替换、回退 | 不实现下载与解压（复用 `download`/`archive`） |
| `internal/manifest` | 清单拉取、解析、校验、缓存、出厂快照降级 | 不决定"装到哪" |
| `internal/download` | 下载引擎：多镜像测速、续传、重试、代理、进度 | 不解析清单、不解压 |
| `internal/archive` | 归档识别与解压（zip / tar.gz / tar.xz / 7z / tar） | 不下载、不写环境变量 |
| `internal/install` | 安装编排：按 `install_kind` 走不同分支，自检，后置操作 | 不直接发 HTTP（走 `download`） |
| `internal/envvar` | 环境变量读写：Windows 注册表协议、Unix shell 协议、备份回滚 | 不做下载、不做 UI |
| `internal/detect` | 检测：组件是否已装、装在哪、版本多少 | 不擅自修改任何东西（只读） |
| `internal/component` | 组件模型定义、内置出厂快照的读取 | 不联网 |
| `internal/logging` | 日志：分级、落盘、轮转、脱敏 | 不决定向用户显示什么 |
| `internal/i18n` | 面向用户的文案与人话映射模板 | 不含业务逻辑 |
| `internal/ui` | Wails 绑定层：把 internal 能力暴露给前端 | 不写业务规则（只做参数校验与转发） |

**依赖方向必须单向**：`ui → app → {update, install, detect, manifest} → {download, archive, envvar, paths, component, logging}`。
任何反向依赖（下层 import 上层）都视为设计事故。

## 1.3 命名规范

- 包名：小写、单数、无下划线（`envvar` 而不是 `env_vars`）。
- 文件：小写下划线，体现内容（`registry_windows.go`、`shell_unix.go`、`pointer.go`）。
  平台相关文件用 Go 的构建约束后缀：`_windows.go` / `_darwin.go` / `_linux.go`。
- 导出类型：名词（`Pointer`、`Manifest`、`Package`）。
- 接口：能加 `-er` 就加（`Downloader`、`Verifier`），且**接口定义在使用方**（Go 惯例）。
- 错误变量：`ErrXxx`（`ErrChecksumMismatch`、`ErrNoUsableVersion`）。
- 常量：不使用全大写，用驼峰（`DefaultTimeout`）；枚举值用带前缀的类型化常量。
- 布尔量：用 `is`/`has`/`should` 前缀，避免 `flag`、`enable` 这类含糊词。
- 单位写进名字：`Timeout`（`time.Duration`）、`SizeBytes`、`PercentDone`，杜绝"这个数字是秒还是毫秒"。

## 1.4 注释规范（本项目的核心要求）

### 1.4.1 三种注释，各有明确用途

| 类型 | 位置 | 必须回答的问题 |
|---|---|---|
| **文件头注释** | 每个 `.go` 文件第 1 行起 | 这个文件负责什么功能？它的边界在哪？ |
| **符号注释** | 每个导出的类型/函数/常量前 | 功能是什么？参数含义？失败会怎样？ |
| **流程注释** | 长函数内部 | 现在走到哪一步了？为什么这么做？ |

### 1.4.2 文件头注释模板

每个文件开头必须有一句"本文件负责……"，再补一句边界说明。示例（示意格式，非实现代码）：

```
// 本文件负责：把用户的编程环境目录（ENV_ROOT）里的组件安装结果同步到环境变量。
// 边界：只做"写入与撤销"，不做下载与解压；不判断装哪个版本（由 install 决定）。
// 平台：本文件为 Windows 专用（注册表），Unix 见 shell_unix.go。
```

### 1.4.3 符号注释必须包含"失败会怎样"

对外函数一律按下面四段写（有则写，无则省略小标题）：

- **功能**：一句话，动词开头。
- **参数**：非自明的参数必须解释（尤其是路径、超时、是否允许网络）。
- **返回 / 失败**：什么情况返回什么错误，调用方该怎么处理（重试？提示用户？放弃？）。
- **副作用**：会写盘吗？会改注册表吗？会启动子进程吗？——**这一条对本项目至关重要**，
  因为我们的代码会动用户的电脑。

### 1.4.4 流程注释只在"为什么"上花笔墨

- 代码能表达"是什么"，所以不要写 `// 把 i 加一`。
- 必须写的是：**为什么这样、为什么不能那样、边界在哪、坑在哪**。
  例如写"这里必须先备份再改：注册表写入成功但广播失败时，用户可能重启后才发现，
  有备份才能一键还原"。
- 多步骤流程用统一步骤号，方便讨论时指位：
  `// 步骤 3：校验解压结果，任一文件缺失即整批作废`

### 1.4.5 待办与遗留

固定格式，必须带模块和原因，杜绝"以后再优化"这种空话：

```
// TODO(envvar): 支持 fish shell —— 目前只处理 zsh/bash/profile，fish 用户会落到 profile
// FIXME(download): 分片续传在服务端不支持 Range 时会静默退化为全量重下，需要提示用户
```

### 1.4.6 禁止的注释

- 复述代码的注释（`// 循环遍历数组`）。
- 残留的注释掉的代码块（要么删掉，要么用 `// 保留原因：` 说明为什么留着）。
- 与代码不一致的注释 —— **比没有注释更糟**。改动逻辑时必须同步改注释，
  这作为 Code Review 的必查项。
- 表情符号、无信息量的分隔线刷屏。

## 1.5 错误处理规范

这一节是"没有静默失败"原则在代码层的落地。

### 1.5.1 三条硬规则

1. **禁止 `_ = err`。** 确需忽略时必须写成
   `// 忽略原因：清理临时文件失败不影响结果，仅记录日志`，并在同一行调用 `logging.Warn`。
2. **错误必须带上下文**：哪个组件、哪个版本、哪个 URL、哪个路径。
   使用 `fmt.Errorf("下载 %s 的 %s 失败: %w", comp, version, err)` 形式包装，保留 `%w` 链路。
3. **错误必须最终被"看见"**：要么被处理重试，要么冒泡到 UI，要么明确记录为日志中的 error 级。
   绝不允许"某处返回了错误，调用方没检查也没记录"。

### 1.5.2 错误分类（决定重试策略与用户文案）

每一个错误在冒泡到 UI 前必须被归入下列类别之一，类别决定"能不能自愈"和"怎么对用户说"：

| 类别 | 例子 | 是否自动重试 | 对用户怎么说 |
|---|---|---|---|
| 网络暂时不可用 | 连接超时、DNS 失败 | 是（换镜像、退避） | "网络好像不通，我们换了个下载地址再试" |
| 上游资源变更 | 404、校验和改变 | 是（重新拉清单） | "官方更新了这个版本，我们正在重新获取信息" |
| 磁盘问题 | 空间不足、写入被拒 | 否 | "磁盘空间不够 / 文件被占用，请关闭其他程序后重试" |
| 权限问题 | 拒绝访问 | 否（不尝试提权） | "这个位置需要管理员权限，请换个位置或按提示操作" |
| 用户取消 | 用户点了取消 | 否 | 不报错，安静回到初始状态 |
| 程序缺陷 | 解析异常、空指针 | 否 | "程序内部出错了，已记录日志" + 诊断包入口 |

### 1.5.3 panic 策略

- 业务代码**禁止 panic**。
- 只允许在启动最早期（配置无法解析、路径无法确定）panic，并保证被启动器捕获为退出码。
- 所有后台 goroutine 必须有 `defer recover()`，把 panic 转成错误并记日志——
  一个后台任务的 panic 不能让用户看到一个白窗口。

## 1.6 日志规范

- 分级：`debug`（开发用，默认关）/ `info`（用户可理解的进展）/ `warn`（降级但继续）/
  `error`（失败）。
- **结构化字段**：时间、级别、模块、组件、动作、耗时、结果。便于用户导出诊断包后我们能直接分析。
- **脱敏**：用户名、家庭路径中的用户名、代理地址的账号密码一律不落盘。
- **轮转**：按天切分，保留最近 14 天；单文件超过 10 MB 切分。
- **原则**：日志面向"我们排查问题"，界面文案面向"用户理解发生了什么"。
  两者**分开生成**，不能把日志直接丢给用户看（参考实现把 Python 调用栈打印给用户的教训）。

## 1.7 常量与配置

- 所有"组件、版本、下载地址、校验和"一律来自**清单**，代码里不许出现具体版本号。
- 允许硬编码的常量只有：超时默认值、重试次数上限、并发数上限、日志轮转参数等**策略值**，
  且全部集中在一个 `internal/config` 或对应包的常量区，附注释说明取值理由。
- 出厂快照由 `tools/` 里的脚本生成并提交，不允许手写。

## 1.8 分步交付（对应"可以分步来写"）

每个阶段结束时必须**可运行、可演示、可验收**，不允许出现"写了一半跑不起来"的阶段：

| 阶段 | 交付形态 | 验收方式 |
|---|---|---|
| A | 命令行程序：能读清单、下一个组件、验校验和、解压到指定目录 | 用一条命令装好 MinGW 并打印版本 |
| B | 命令行程序：能配环境变量、能自检、能回滚 | 新开终端能跑 `gcc --version`；备份可还原 |
| C | 图形程序：引导式界面走完"选组件 → 装 → 验证 → 告诉用户" | 一个没写过代码的人独立完成一次安装 |
| D | 自更新：清单更新 + 程序更新 + 启动健康检查 + 自动回退 | 故意发一个损坏版本，程序自动回到旧版 |
| E | 云端巡检与发布流水线 | 上游发新版本后 24 小时内清单自动更新 |

**先命令行、后图形**，因为命令行能跑通就说明内核正确；图形层出问题时,
我们可以随时用命令行复现，避免"到底是内核错还是界面错"的扯皮。

## 1.9 工具链与 CI 门禁

- 格式化：`gofmt` / `goimports`，**未格式化的代码禁止合入**。
- 静态检查：`go vet` + `golangci-lint`（启用 `errcheck`、`staticcheck`、`ineffassign`；
  `errcheck` 是"没有静默失败"的自动化保障）。
- 测试：`go test ./...`；涉及文件系统与注册表的模块必须有测试；CI 三平台都跑。
- 覆盖率：核心包（`download`、`archive`、`envvar`、`update`、`manifest`）行覆盖率不低于 70%。
- 提交前检查单：注释是否同步更新、是否引入硬编码版本号、是否有吞错、是否有新依赖
  （新依赖需说明理由，本项目目标是**尽量少依赖**）。

---

## 1.10 版本与提交规范

- 程序版本：语义化版本 `主.次.补丁`；`min_supported` 只在必须强制升级时提升。
- 清单版本：独立于程序版本，单独计时（清单更新远比程序更新频繁，见 `03`、`04`）。
- 提交信息：`类型(模块): 说明`，类型用 `feat` / `fix` / `docs` / `refactor` / `test` / `chore`。
  说明必须写清"改了什么、为什么"。
- 每个功能一个分支、一个可回滚的提交序列；大改动用 `feat!` 标记并在文档中同步更新设计。

## 1.11 红线清单（Code Review 一票否决项）

1. 吞掉错误或 `_ = err` 未说明原因。
2. 修改 `HKLM` 或系统级环境变量。
3. 删除非本程序创建的文件/目录。
4. 在代码里硬编码组件版本号或下载地址。
5. 未经备份就修改用户环境变量。
6. 使用 `verify=False` / 跳过证书校验。
7. 面向用户的界面文案直接拼接原始错误字符串。
8. 未加锁的共享状态、无 `recover` 的后台 goroutine。
9. 注释与实现不一致。
10. 引入未经讨论的第三方依赖。
