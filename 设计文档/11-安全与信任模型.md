# EnvReady 设计文档 11 —— 安全与信任模型

> EnvReady 会做三件"有权限"的事：**下载并解压第三方程序、执行子进程、修改用户环境变量**。
> 因此必须先把威胁想清楚：谁可能让这三件事变坏。

---

## 11.1 威胁模型

| # | 威胁 | 后果 | 对策（本文档对应章节） |
|---|---|---|---|
| T1 | 传输被劫持（公共 WiFi、中间人） | 下载到被篡改的包 | TLS + 强制证书校验 + 校验和（11.3、11.4） |
| T2 | **清单被篡改**（托管仓库被入侵 / CDN 被投毒） | 清单把下载指向攻击者地址，安装任意程序 | 清单签名 + 来源白名单（11.3、11.5） |
| T3 | 上游官方包本身被投毒 | 用户装到恶意程序 | 无法完全防御；至少做到"来源可追溯 + 哈希固定"（11.5、11.9） |
| T4 | 我们执行了清单里的任意命令 | **命令注入 / 任意代码执行** | 命令白名单 + 不用 shell 拼接 + 只执行我们装的二进制（11.7） |
| T5 | 用户环境被我们改坏 | 电脑命令行不可用 | 备份、意图记录、回滚、只写用户级（见 `07`） |
| T6 | 杀软误报 / 系统拦截 | 程序被删、下载被拦 | 不压缩壳、申请签名与公证、明确说明（11.8） |
| T7 | 提权滥用 | 用户失去信任、系统被改 | 首期完全不提权、不写 HKLM（11.6） |
| T8 | 隐私泄露 | 用户信息外泄 | 不收集个人信息、匿名统计默认关闭、日志脱敏（11.10） |
| T9 | 依赖链被投毒（Go 第三方包） | 引入后门 | 依赖最小化 + 锁定 + 定期审查（11.11） |
| T10 | 我们的账号/CI 被入侵 | 发布带毒版本 | CI 权限最小化、分支保护、发布需人工确认（11.11） |

## 11.2 信任根链条

```
① 硬编码在客户端内的公钥
       └──验签──→  ② client.json / components/*.json（清单）
                        └──比对 sha256──→  ③ 下载到的安装包
                                              └──逐文件校验──→  ④ 解压后的文件
                                                                  └──实际执行自检命令──→  ⑤ "真的能用"
```

**链条的关键性质**：

- 第 ①环是唯一的"信任锚"。它编译在程序里，改它必须重新发版（并且发版是可审计的）。
- **第 ②环比第 ③环更重要**：攻击者若能改清单，就能把下载地址指向自己，
  再配一个"哈希对得上"的恶意包——**单看包哈希完全无法发现**。
  因此"签清单"的优先级高于"签每个包"。
- 第 ⑤环是最后一道：即使前面都对，装出来的东西也可能因为缺少依赖而不可用，
  自检是唯一能发现它的手段。

## 11.3 签名方案

| 阶段 | 方案 | 状态 |
|---|---|---|
| 首期 | **无签名**（`signature: null`） | **明确记录为降级状态**，不是"已完成" |
| 第二期 | **minisign** 签 `client.json` 与每个组件分片；公钥硬编码进客户端 | 计划 |
| 备选 | cosign（生态更完整、与容器签名体系一致，但引入依赖更重） | 备选 |

**无签名期间的补偿措施**（必须做到，否则首期的风险不可接受）：

1. **来源白名单**（见 11.5）——即使清单被改，也无法把下载指向非官方域名。
2. **校验和固定**——清单里每个版本的哈希由 CI 生成，篡改清单必须同时篡改哈希，
   这就要求攻击者能提交到仓库（而不是只污染 CDN 缓存）。
3. **Git 提交历史公开可审计**——清单仓库的每次变更都在公开历史里，异常变更可被发现。
4. **分片哈希**：`index.json` 里带每个分片的 `manifest_sha256`，
   使攻击者必须同时污染索引与分片（提高门槛，但不构成完整防御）。

**已知残余风险必须写进文档**：无签名状态下，能写入清单仓库的攻击者可以让客户端
安装任意程序。这是首期的**已知限制**，用"仓库保护 + 双人复核 + 审计日志"来缓解。

## 11.4 传输安全

| 规则 | 说明 |
|---|---|
| **永远校验证书** | 禁止任何形式的"证书错误就跳过"。参考实现里存在第三次重试时 `verify=False` 的降级逻辑，这是**不可接受**的：它把一次可解释的网络故障变成了一个静默的安全漏洞 |
| 只用 HTTPS | 不接受 `http://` 的下载地址（清单校验阶段就拒绝） |
| TLS 最低版本 | 1.2 以上 |
| 失败时的行为 | 明确报"安全连接建立失败"，并给出排查建议（系统时间是否正确、是否有代理拦截），**绝不降级到不安全连接** |
| 重定向 | 限制跳转次数（如 5 次），且**跳转目标也必须过来源白名单** |

## 11.5 来源白名单

**这是无签名阶段最重要的防线。**

规则：清单里的每个 `mirrors` 前缀与最终解析到的 URL，其**主机名必须属于许可列表**。

```
许可列表（按组件维护，示例）：
  *.python.org
  nodejs.org / *.nodejs.org
  api.adoptium.net / github.com / release-assets.githubusercontent.com
  archive.apache.org / dlcdn.apache.org
  sourceforge.net / *.dl.sourceforge.net（含其镜像域名）
  winlibs.com / github.com
```

| 情形 | 处理 |
|---|---|
| 清单中的地址不在白名单 | **拒绝使用该地址**，记 error 日志，回退到缓存/出厂快照 |
| 重定向落到非白名单域 | 中止下载 |
| 需要新增白名单域 | 必须修改客户端代码（→ 发版），因此白名单是**代码里的常量**，不是清单里的字段 |

**为什么白名单必须在代码里**：如果白名单本身来自清单，攻击者改清单即可同时改白名单，
防线失效。白名单写死在代码里意味着"新增一个下载域必须发一次新版"，
这个代价换来的是"清单被篡改也无法把用户引到任意域名"。

## 11.6 权限最小化

| 规则 | 说明 |
|---|---|
| 首期完全不提权 | 不触发 UAC；全部安装到用户可写目录 |
| 不写 `HKLM` | 只写 `HKCU\Environment`（见 `07`） |
| 不写系统目录 | 不安装到 `Program Files`、`/usr/local`（除非用户显式选择且自行提权） |
| 不请求管理员权限的组件 | 若某组件只能以管理员安装（部分数据库的官方安装器），则**明确告诉用户"这个需要管理员权限，我们要请你确认"**，并让用户自己决定；不做绕过 |
| 不关闭安全软件、不改注册表安全设置 | 绝不 |
| 不修改防火墙、不开放端口 | 首期组件都是本地工具链，不需要 |

## 11.7 子进程执行安全（T4 的落地）

我们确实需要执行子进程（自检命令、官方安装器、7zr），这是必须防住的一面。

| 措施 | 说明 |
|---|---|
| **不使用 shell** | 所有子进程调用传数组参数，不经 `cmd /c` 或 `sh -c` 拼接字符串（避免命令注入） |
| **命令只来自清单的受限字段** | `verify.command` 只允许是"相对路径的可执行文件"或"我们已知的固定命令名"（如 `gcc`），不允许 shell 元字符 |
| **执行前校验可执行文件位置** | `verify.command` 指向的文件必须位于该组件自己的安装目录内（或系统命令解析结果），不允许指向任意路径 |
| **参数不允许自由文本** | `verify.args` 是字符串数组，逐项校验不含 `;` `|` `&` `` ` `` `$(` 等元字符 |
| **安装器的静默参数来自清单但受白名单约束** | 例如只允许短参数与已知开关形式 |
| **7zr 的来源固定** | 只从 `7-zip.org` 官方地址下载，且校验其哈希（哈希硬编码在程序中） |
| **工作目录固定** | 子进程 `cwd` 设为组件目录，避免误操作其他位置 |
| **超时与输出上限** | 每个子进程都有超时；stdout/stderr 有长度上限（防止恶意程序刷爆日志） |

**这条防线是"无签名阶段"的必要补充**：即使清单被改，攻击者也无法让客户端执行任意命令，
最多只能执行"某组件目录下的某个文件"，而这个文件本身也过了哈希校验。

## 11.8 防误伤（杀软、系统拦截）

| 措施 | 说明 |
|---|---|
| **不使用 UPX 等压缩壳** | 压缩壳会显著提高杀软误报率。体积大几十 MB 换来"不被当成病毒"是值得的交易 |
| 申请代码签名证书 | Windows 上用 Authenticode 签名，可显著降低 SmartScreen 拦截；macOS 需要公证（notarization） |
| **首期若无法签名，必须明确告知** | macOS 上未签名的应用需要用户手动处理（参考实现让用户执行 `xattr -cr`），我们要在下载页与文档里把这一步写清楚 |
| 不修改系统安全设置 | 见 11.6 |
| 对误报提供解释 | 帮助页提供"为什么会被安全软件警告"的说明与官方下载链接说明 |

## 11.9 上游包的溯源与"不能做什么"

| 能做的 | 不能做的 |
|---|---|
| 记录来源页面、下载地址、校验和、获取时间 | 无法证明上游包本身没有后门 |
| 用哈希把"我们验证过的那一份"固定下来 | 无法保证上游不会在下一版本投毒 |
| 在界面上显示来源（"来自 python.org"） | 不能替上游背书 |
| 优先选择官方推荐的构建分发（如 winlibs 之于 MinGW） | 不使用来路不明的第三方打包版 |

**这条"能/不能"的边界必须写进用户文档**，避免我们给出虚高的安全承诺。

## 11.10 隐私

| 项 | 决定 |
|---|---|
| 账号 | 不需要，不做 |
| 个人信息 | 不收集（不采集姓名、学号、邮箱、IP 上报） |
| 匿名统计（版本号、平台、成功率） | **字段预留但默认关闭**，用户可在设置中显式开启 |
| 日志 | 含用户名与路径，属于本地文件，**未经用户点击"复制诊断信息"绝不上传** |
| 上传内容 | 若用户主动提交诊断信息，上传前在界面上展示将要发送的内容并可编辑 |

**"展示将要发送的内容"是刻意设计**：这既是隐私要求，也是建立信任的方式
（学生怕"这个软件偷我东西"，能看见就不可怕）。

## 11.11 供应链与 CI 安全

| 项 | 措施 |
|---|---|
| Go 依赖 | **最少化**（优先标准库）。每新增一个依赖必须在文档中说明理由 |
| 依赖锁定 | 使用 `go.sum` 与模块版本锁定，CI 中校验未被篡改 |
| 依赖审查 | 定期检查依赖的已知漏洞（`govulncheck`）与维护状态 |
| GitHub Actions | 固定到具体 commit/tag，不使用浮动的 `@main`；权限最小化（默认只读） |
| 发布权限 | 发布 Release 需要人工确认；清单仓库的巡检提交使用只对该仓库有写权限的机器人 token |
| 分支保护 | 主分支与清单仓库主分支均需 PR 与复核 |
| 敏感信息 | CI 中不打印 token；不在代码中硬编码任何密钥 |

---

## 11.12 事件响应（清单被污染怎么办）

必须提前想好，因为这类事故的代价是"所有还在拉清单的用户"。

| 步骤 | 动作 | 目标时间 |
|---|---|---|
| 1 | 回滚清单提交（`git revert`），CDN 缓存刷新 | 分钟级 |
| 2 | 若涉及下载地址被改，**提升 `min_supported` 强制客户端升级**，或发布一个"忽略该清单"的补丁版本 | 小时级 |
| 3 | 在发布页与仓库 Issue 公告说明影响范围与处置 | 小时级 |
| 4 | 检查已下载用户的哈希记录（客户端本地存有下载记录，可帮助用户自查） | 天级 |
| 5 | 复盘：签名机制是否已到位、白名单是否被绕过、复核流程是否失效 | 周级 |

**这就是为什么第 11.3 节的签名必须做**：无签名阶段的第 2 步只能靠"强制升级"，
而强制升级本身也依赖清单——**如果清单不可信，我们连"叫用户升级"都做不到**。
这个循环只有签名能打破，因此签名应当尽早落地。
