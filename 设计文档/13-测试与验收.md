# EnvReady 设计文档 13 —— 测试与验收

> 本项目的可信度不来自"功能列表"，而来自**可重复的验证**。
> 对应申报指标：单次部署由 30 分钟以上压缩到 **5 分钟以内**、**成功率 ≥ 90%**、
> 关键操作 **100% 可回滚**、上游变更后 **24 小时内同步**。
> 本文档说明这些指标怎么被测量，而不是怎么被宣称。

---

## 13.1 测试分层

| 层 | 测什么 | 工具与方式 | 何时跑 |
|---|---|---|---|
| 单元 | 纯逻辑：PATH 归一化、清单解析、指针状态机、断点续传元数据 | `go test`，标准库 `testing` + `httptest` | 每次提交 |
| 集成 | 模块协作：下载→校验→解压→落盘，环境变量写入→回读 | `httptest` 起本地服务器提供假包；Windows 注册表用临时子键 | 每次提交 |
| 端到端 | 真机完整流程：从空机器到 `gcc --version` 可用 | 三平台虚拟机 + 自动化脚本 | 每阶段 / 发版前 |
| 故障注入 | 崩溃与异常路径（`02` 的恢复矩阵 13 行） | 在半途杀进程/断网/塞满磁盘，重启后断言状态 | 每阶段 |
| 兼容 | 已有环境、各种 shell、超长 PATH、非英文用户名 | 参数化 + 手工清单 | 发版前 |
| 性能 | 启动耗时、安装耗时、内存占用、进度上报频率 | 计时与采样 | 每阶段 |

## 13.2 单元测试重点（必须覆盖的部分）

| 模块 | 关键用例 |
|---|---|
| `envvar`（Windows） | PATH 切分/合并；大小写不同视为同一条；尾斜杠等价；`%VAR%` 不展开也能比较；`REG_EXPAND_SZ` 类型保持；值为空/仅分隔符的边界；超长 PATH（>2000 字符） |
| `envvar`（Unix） | 块的幂等替换；块不完整时报错而不追加；CRLF/LF 保持；末尾无换行时补换行；fish 语法分支；切换版本后旧条目被整条替换（**断言 PATH 中该组件只出现一次**） |
| `paths` | 三平台路径推导；`XDG_DATA_HOME` 设置与未设置；用户名含空格/中文 |
| `update` | 指针状态机全部转移（含 `prev` 缺失、`broken` 目录存在）；原子写（写 tmp 后 rename）；`attempts` 上限；修复模式的候选选择顺序 |
| `manifest` | schema 校验；未知字段忽略；未知 `schema` 降级；签名缺失/无效的处理；缓存与出厂快照的优先级 |
| `download` | `.part.meta` 往返；206 续传起点校验；返回 200 时丢弃分片；ETag 变化时重下；校验和边下边算（含续传时从头重算）；`Content-Range` 解析 |
| `archive` | 魔术字节识别（含"扩展名 .tar、实际 gzip"）；`strip_root` 两种；zip 中的符号链接与权限位（macOS 必须保留）；损坏包的报错 |
| `detect` | 四级检测顺序（自管记录 → PATH → 常见安装路径 → 环境根扫描）；半成品（缺关键文件）判为不可用；多版本共存时的激活版本判定 |

**覆盖率门禁**：`download` / `archive` / `envvar` / `update` / `manifest` 行覆盖率 ≥ 70%。

## 13.3 集成测试：用本地假上游

不起真实网络请求（避免测试依赖外网、也避免把测试流量打给上游）：

```
httptest.Server 提供：
  /client.json                     假客户端清单
  /components/index.json            假索引
  /components/mingw.json            假分片
  /pkg/mingw-14.2.0.zip             动态生成的小号 zip（内含假的 gcc 脚本）
  /pkg/broken.zip                   内容与哈希不符的包
  /pkg/slow                       故意慢速响应（测进度与超时）
  /pkg/no-range                    不返回 206（测"不支持续传"路径）
  /pkg/redirect-signed             302 到带过期参数的地址（测签名过期重解析）
  /pkg/html-200                    返回 200 + HTML 错误页（测"伪装成功"识别）
```

用这些端点可以覆盖 `06` 里的几乎所有分支，**无需真实网络**。

## 13.4 故障注入（把恢复矩阵变成测试）

`02` 的崩溃恢复矩阵 13 行 → 13 个自动化用例。实现方式：

- 在代码中预留测试钩子：环境变量 `ENVREADY_TEST_CRASH_AT=<阶段名>` 使程序在指定阶段直接 `os.Exit`。
  该钩子必须在正式构建中被编译期排除（构建标签），避免成为真实缺陷。
- 或者更干净的做法：用外部脚本在观察到特定日志行后杀进程。

| 用例 | 断言 |
|---|---|
| 下载中杀进程 → 重启 | 续传成功且最终 SHA-256 正确 |
| 解压中杀进程 → 重启 | `.stage-` 被清理，旧版本仍可用 |
| 写指针前杀进程 | 指针未损坏；已有版本可启动 |
| 写指针后、启动前杀进程 | 进入 pending 观察流程 |
| 健康检查失败 → 回退 | 指针回到 `prev`，失败目录变成 `.broken-`，用户可见告知 |
| 环境变量写一半杀进程 | 出现意图记录；重启后给出"完成/还原"选择；两种选择都得到一致状态 |
| 磁盘塞满 | 在开始前失败（预检）或失败后不留半成品；无部分写入的 PATH 条目 |

## 13.5 环境变量专项测试（风险最高）

必须在**真实的三平台机器**上跑一组"已有配置"的组合：

| 场景 | 期望 |
|---|---|
| 用户 PATH 已含同一路径但大小写不同 | 不重复添加 |
| 用户 PATH 已含同一路径但带尾斜杠 | 不重复添加 |
| 用户 PATH 含有 `%USERPROFILE%\bin` | 原样保留，不被展开成硬编码路径 |
| 用户 PATH 长度 > 2000 字符 | 正常写入且不回读失败；给出"PATH 偏长"的提示 |
| 用户名含空格或中文 | 全流程正常（路径加引号的边界） |
| 之前已被参考实现（murig）改过 | 能检测到旧的 `env-auto-setup` 标记块，**能识别并询问是否清理**，不重复追加 |
| zsh / bash / fish 三种 shell | 写入正确文件、正确语法；fish 不出现 bash 语法 |
| 从 Finder 启动（`$SHELL` 为空，macOS） | 仍能通过账号数据库确定 shell，写对文件 |
| 配置文件被用户改成 CRLF | 保持 CRLF，不引入混合行尾 |
| 配置文件中有我们标记块但不完整 | 报错并让用户选择，**不追加第二个块** |
| 一键还原 | 与备份逐字节一致 |

## 13.6 端到端（真机、干净环境）

**环境准备**：三平台各维护一份虚拟机快照，状态为"全新系统 + 无任何开发工具"。
每次 E2E 从快照恢复，保证结果可复现。

**E2E 用例（首期 5 类环境）**：

| # | 用例 | 通过标准 |
|---|---|---|
| 1 | Windows 全新机器装 C/C++ | 新开 cmd，`gcc --version` 输出含版本号；示例项目在 VS Code 中可编译、可断点调试 |
| 2 | Windows 全新机器装 Python | `python --version` 与 `pip --version` 均可用（**特别检查 pip 可用**：参考实现用 embeddable 包导致无 pip，是 S19 缺陷） |
| 3 | Windows 全新机器装 Java | `java -version`、`javac -version` 输出正确 |
| 4 | macOS 装 C/C++ 与 Node | 同上；检查 `.app` 类组件的符号链接完好（若涉及） |
| 5 | Linux 装 Python 与 Java | 同上；检查 shell 配置文件写入正确 |
| 6 | 连通性：装完后立刻在**新窗口**验证 | 不依赖重启系统 |
| 7 | 卸载后 | PATH 与 `XXX_HOME` 不残留；已装环境目录按用户选择处理 |
| 8 | 网络中断测试 | 断网后安装给出明确错误与出路，不产生半成品 |

**时间度量**：用例 1 从"双击程序"到"新窗口 `gcc --version` 有输出"计时，
目标 **≤ 5 分钟**（在 10 Mbps 网络下）。这条指标必须实测记录，不能估算。

## 13.7 成功率度量方法

申报指标"成功率不低于 90%"，需要明确的度量口径：

| 项 | 定义 |
|---|---|
| 一次部署 | 用户从"选择 C/C++"到"看到结果页"的完整过程 |
| 成功 | 结果页显示为成功**且**自检命令在**新开窗口**中通过 |
| 失败 | 其余情况（含用户取消——**取消单独统计，不计入失败率**） |
| 样本一 | 自动化：在同一台机器上重复执行 100 次完整部署（每次先回滚到快照） |
| 样本二 | 真实用户：30 名学生（不同网络环境：宿舍 WiFi / 机房有线 / 手机热点）各完成 1 次 |
| 报告 | 分别给出两组的成功率与失败原因分布（按 `error_class` 分组） |

**为什么两个样本都要**：自动化样本能排除"人的因素"验证内核；
真实样本才能暴露网络与使用习惯导致的问题。只有后者能支撑"面向学生的成功率"这一说法。

## 13.8 试用方案（对应"不少于 2 轮试用"）

| 轮次 | 时间 | 对象 | 交付 | 回收 |
|---|---|---|---|---|
| 第 1 轮 | 客户端图形版可用后 | 本科编程入门课程的学生（或计算机社团）10–15 人 | 安装包 + 一页说明 | 观察记录 + 简短问卷 |
| 第 2 轮 | 修复第 1 轮问题后 | 扩大到 2 个班级/社团，≥30 人 | 同上 + 帮助页 | 问卷 + 5 场访谈 |

**观察法（第 1 轮必须做）**：让 3–5 名学生**当面操作**，我们在旁边**只记录不提示**，
记录以下数据：

- 第一屏停留时长与第一句话（他在找什么）
- 是否读提示文字（眼动/复述法：请他说出"现在在做什么"）
- 卡住的第一个位置
- 是否需要帮助；需要帮助的具体问题

这类数据比问卷更能暴露交互问题（学生在问卷里往往会说"挺好的"）。

**回收目标**：有效问卷 ≥ 50 份、访谈 ≥ 5 场。

## 13.9 回归测试（清单驱动带来的新要求）

因为"能用清单解决的不改程序"，**清单变更本身就是一次可能引发事故的发布**，因此：

| 变更类型 | 必须的回归 |
|---|---|
| 新增版本（同组件） | 用该版本跑一次 E2E 的下载+解压+自检（至少在一个平台） |
| 修改 `recommended` | 在三个平台的干净虚拟机上各跑一次完整部署 |
| 修改下载地址 | 全平台自动化校验（`10` 的 verify 阶段） |
| 新增组件 | 全平台 E2E + 环境变量专项测试 |
| 修改清单 schema | 旧客户端兼容测试（用上一个发布版程序读新清单） |

**"旧客户端读新清单"这条必须测**：否则一次 schema 变更会让所有未升级的用户直接不可用。

## 13.10 发版前手动检查清单

自动化测不了的部分，每次都过一遍：

1. 在一台**从未装过任何开发工具**的 Windows 机器上走完整流程（不做任何手工干预）。
2. 界面上**不出现**技术黑话（对照 `08` 的映射表逐屏检查）。
3. 故意断网，确认错误信息给出三条出路。
4. 故意把 PATH 改得很长，确认不截断。
5. 检查日志里**不含**用户名、完整 URL 查询串、IP。
6. 检查卸载后注册表与配置文件无残留（用脚本比对）。
7. 下载页/文档里对"未签名"的说明是否与当前实际状态一致（不能多写也不能少写）。
8. 更新一次版本，确认旧版本被清理、新版本可用、`current.json` 状态为 `stable`。
