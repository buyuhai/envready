# EnvReady 设计文档 04 —— 资源清单规范

> 清单是 EnvReady 的"数据层"。**本项目的核心设计决定之一是：能用清单解决的，绝不改程序。**
> 新增一个语言环境、换一个下载地址、调整推荐版本，都只改 JSON，不需要发新版程序。
> 清单的拉取、缓存与降级策略见 `03` 与 `06`；清单的签名见 `11`。

---

## 4.1 三类清单，按变化频率分离

| 清单 | 内容 | 变化频率 | 拉取时机 | 体积目标 |
|---|---|---|---|---|
| `client.json` | 客户端自身的版本与安装包 | 低（发版才变） | 启动后延迟 5 秒，每 24 小时最多一次 | < 10 KB |
| `components/index.json` | 组件目录（画卡片用） | 中 | 启动后延迟 1 秒（带 ETag） | < 30 KB |
| `components/<key>.json` | 单个组件的版本与下载信息 | 高（上游发版就变） | 用户点开该组件时才拉（懒加载） | < 50 KB |

### 为什么必须按组件分片

实测参考实现所能拉到的版本数量差异极大：

| 组件 | 在线版本数 |
|---|---|
| Node.js | 289 |
| Tomcat | 202 |
| Python | 166 |
| Maven | 46 |
| Elasticsearch / Redis / Kafka / Hadoop… | 10–15 |
| 达梦 DM8 | 1 |

如果合并成一个总清单，每次启动都要下载并解析几百 KB 到几 MB 的数据，其中 99% 用不上。
分片之后：

- 首屏只拉索引（几 KB）就够画出所有卡片。
- 用户点开哪个组件才拉哪个分片。
- **云端巡检 CI 也只改动受影响的单个文件，Git diff 干净可审**，出问题能一眼看出是哪个组件的地址变了。

## 4.2 `client.json`

```json
{
  "schema": 1,
  "channel": "stable",
  "latest": "1.1.0",
  "min_supported": "1.0.0",
  "published_at": "2026-10-16T10:00:00Z",
  "notes": {
    "zh-CN": "修复了下载中断后必须从头开始的问题。",
    "en": "Fixed an issue where an interrupted download had to restart from scratch."
  },
  "mirrors": [
    "https://cdn.jsdelivr.net/gh/<org>/envready-dist@v1.1.0/",
    "https://github.com/<org>/envready/releases/download/v1.1.0/"
  ],
  "packages": {
    "windows-amd64": { "file": "envready-1.1.0-windows-amd64.zip",   "size": 18432000, "sha256": "…", "format": "zip" },
    "windows-arm64": { "file": "envready-1.1.0-windows-arm64.zip",   "size": 17890000, "sha256": "…", "format": "zip" },
    "darwin-arm64":  { "file": "envready-1.1.0-darwin-arm64.tar.gz", "size": 17980000, "sha256": "…", "format": "tar.gz" },
    "darwin-amd64":  { "file": "envready-1.1.0-darwin-amd64.tar.gz", "size": 18300000, "sha256": "…", "format": "tar.gz" },
    "linux-amd64":   { "file": "envready-1.1.0-linux-amd64.tar.gz",  "size": 17200000, "sha256": "…", "format": "tar.gz" }
  },
  "launcher": { "version": "1.0.1", "packages": { "…": "…" } },
  "signature": null
}
```

| 字段 | 说明 |
|---|---|
| `channel` | 通道：`stable` / `beta`。首期只发布 `stable`，字段保留以便日后开灰度 |
| `latest` | 最新版本号；客户端与自身版本比较 |
| `min_supported` | 低于此版本**强制更新**（仅用于安全修复）；不轻易提升 |
| `notes` | 面向用户的更新说明，**必须是人话**，按语言分。不写 commit 列表 |
| `mirrors` | URL **前缀列表**；与 `packages[x].file` 拼成完整地址 |
| `packages` | 按 `平台-架构` 分。**注意：必须包含 `windows-arm64`**——参考实现已有 arm64 Windows 分支，忽略它会让一类用户完全无法安装 |
| `format` | `zip` / `tar.gz`，与该平台合适的打包方式对应（见 4.6） |
| `launcher` | 启动器单独版本，与主程序解耦。它极少变，但一旦需要变（例如指针格式升级）必须能单独更新 |
| `signature` | 清单签名。首期为 `null` 并**明确记录为降级状态**（见 `11`） |

## 4.3 `components/index.json`

```json
{
  "schema": 1,
  "updated_at": "2026-10-16T09:00:00Z",
  "categories": [
    { "key": "cpp",      "name": "C / C++",     "order": 1, "intro": "写 C 语言程序需要的编译器" },
    { "key": "python",   "name": "Python",      "order": 2, "intro": "最常用的入门语言" },
    { "key": "java",     "name": "Java",        "order": 3, "intro": "很多课程与考试用" },
    { "key": "web",      "name": "网页前端",     "order": 4, "intro": "做网页需要" },
    { "key": "tools",    "name": "常用工具",     "order": 5, "intro": "编辑代码时用得上" }
  ],
  "components": [
    {
      "key": "mingw",
      "name": "C / C++ 编译器（MinGW-w64）",
      "category": "cpp",
      "aliases": ["gcc", "g++", "mingw", "编译器", "C语言", "C++"],
      "summary": "装完即可编译并运行你的第一个 C 程序",
      "recommended_for": ["第一次学 C 语言", "学校的 C 语言课"],
      "manifest": "components/mingw.json",
      "manifest_sha256": "…",
      "supported": true
    }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `categories[].intro` | 一句话告诉学生"这一类是干什么的"，直接显示在界面上（参考实现的分类只有名字，学生不知道"大数据"要不要装） |
| `aliases` | 搜索别名，**做成数据而非硬编码**。学生搜"编译器""C语言""gcc"都应命中 |
| `recommended_for` | 推荐场景，用于界面上的"不知道装什么？"引导 |
| `manifest_sha256` | 分片内容的哈希，防止单个分片被掉包（配合清单签名更完整） |
| `supported` | 该组件当前是否可用。若某个组件的上游彻底失效，置 `false` 并在界面上说明原因，而不是悄悄消失 |

## 4.4 `components/<key>.json`（核心结构）

```json
{
  "schema": 1,
  "key": "mingw",
  "name": "C / C++ 编译器（MinGW-w64）",
  "official": {
    "page": "https://www.mingw-w64.org/",
    "distribution": "winlibs.com（官方推荐的构建分发）",
    "mirror_policy": "直取官方与官方镜像，不由本项目分发"
  },
  "license": "GPL / LGPL / MIT（各子项目不同，详见官方）",
  "env": {
    "home_var": null,
    "path": { "dirs": ["bin"], "position": "append" }
  },
  "requires": [],
  "conflicts_with": [],
  "recommended": "14.2.0",
  "versions": [
    {
      "version": "14.2.0",
      "label": "14.2.0（推荐）",
      "released_at": "2024-08-01",
      "platforms": {
        "windows-amd64": {
          "install_kind": "archive",
          "file": "winlibs-x86_64-posix-seh-gcc-14.2.0-mingw-w64ucrt-12.0.0-r2.zip",
          "size": 112000000,
          "sha256": "…",
          "headers": null,
          "mirrors": [
            "https://github.com/brechtsanders/winlibs_mingw/releases/download/…/",
            "https://mirror.example.org/winlibs/"
          ],
          "archive": { "format": "zip", "strip_root": false }
        },
        "darwin-arm64": { "install_kind": "archive", "archive": { "format": "tar.gz", "strip_root": true }, "…": "…" }
      },
      "post_notes": ["第一次编译前请重新打开命令行窗口，旧窗口不会看到新配置。"],
      "verify": {
        "command": "gcc",
        "args": ["--version"],
        "expect_exit": 0,
        "parse": "gcc \\(.*\\) (\\d+\\.\\d+\\.\\d+)"
      }
    }
  ],
  "versions_all_url": null,
  "notes_for_user": "这是最常用的 C 语言编译器。装好后可以用 VS Code 写代码，用我们生成的配置直接编译运行。"
}
```

### 4.4.1 顶层字段说明

| 字段 | 为什么必须有 |
|---|---|
| `official` | 我们是"替你去官网拿"，来源必须可追溯；同时满足"不托管、不再分发"的定位 |
| `license` | 合规：学生/学校可能关心授权，至少要有指引 |
| `env` | 装完之后环境变量怎么配。`home_var` 为 `null` 表示这个组件只加 PATH、不设 `XXX_HOME` |
| `requires` | 依赖建模。参考实现完全没做（Claude Code 需要先装 Node，只在 README 里写了），我们要在界面上直接提示并支持"一键连带安装" |
| `conflicts_with` | 互斥建模（例如同为 MySQL 协议的数据库可能都占用 3306，或某些工具链不兼容）。首期可以只用于提示 |
| `recommended` | **默认选中的版本**。参考实现把"选版本"这件事丢给小白，是明显的认知负荷（见 `08`） |
| `versions_all_url` | 需要全量版本列表时（高级用户/排错）可选拉取，避免默认清单过大 |
| `notes_for_user` | 卡片上的一句话说明，用人话讲"这个是什么、我为什么要装" |

### 4.4.2 版本条目的字段说明（每个都对应一条实测教训）

| 字段 | 设计动机（教训来源） |
|---|---|
| `version` | 逻辑标识（如 `21`、`14.2.0`）。注意：**它与实际文件名不一定一致**——实测 Adoptium 的 `21` 实际下载到 `OpenJDK21U-jdk_x64_windows_hotspot_21.0.12.1_1.zip`。因此目录名、显示名、下载文件名三者必须分开 |
| `label` | 下拉框显示的文案（如 `21 (LTS)`、`14.2.0（推荐）`）。显示名可变，`version` 不可变 |
| `released_at` | 界面上显示"这是什么时候发布的"。实测有组件默认版本停留在几年前，用户有权知道 |
| `platforms.<平台-架构>` | **显式建模"这个平台没有"**，而不是留空字符串。参考实现实测有 8 个组件在部分平台无包却零提示，用户点了下载才发现失败 |
| `install_kind` | 安装方式：`archive` / `installer` / `npm` / `portable` / `noop`。参考实现用若干布尔字段拼出来，容易漏（它有一个组件的 URL 字段字面量就是字符串 `npm`） |
| `file` / `mirrors` | 文件名与镜像前缀分离，一个包可在多个镜像复用 |
| `size` | 用于下载前的磁盘空间预检与界面提示（实测有单包 1.8 GB） |
| `sha256` | 完整性校验。实测 218 条直链中 26 条异常，其中两个 Python embeddable 版本是**真 404**——官方源也会腐烂，必须校验 |
| `headers` | 防盗链。实测某信创数据库的 OSS 必须带 `Referer` 才允许下载 |
| `archive.format` | `zip` / `tar.gz` / `tar.xz` / `7z` / `tar`。实测有 `.tar` 实为 gzip 的情况，因此**识别应基于文件头魔术字节而非扩展名**（见 `05`） |
| `archive.strip_root` | 解压后是否去掉顶层目录。参考实现用"如果只有一个子目录就进去"的启发式，不够明确、也可能出错 |
| `installer.silent_args` | 安装器模式的静默参数（如 Miniconda 的 `/S` 与 `-b`）。**注意 Windows 上 `/D=路径` 必须放在最后且不能带引号**，这是容易踩的坑 |
| `portable.raw_bin_name` | 便携单文件（如某些 Linux AppImage）下载后需要重命名，方便 PATH 查找 |
| `post_notes` | 装完必须告诉用户的人工操作。**必须渲染在卡片/结果页面上，不能只写日志**（参考实现只打印到日志窗的 warn 行，等于没说） |
| `verify` | **本项目相对参考实现的核心差异**：装完必须实际运行命令并核对版本号，而不是"进度条到 100% 就算成功" |

## 4.5 体积控制策略

| 措施 | 说明 |
|---|---|
| 只放"精选 + 近期" | `versions` 默认放推荐版本 + 最近 8 个；全量列表放到 `versions_all_url` |
| 平台字段按需展开 | 非当前平台的字段可以省略（结构保持一致，值可缺省） |
| 分片懒加载 | 见 4.1 |
| 数字与字符串精简 | 不重复冗长描述；描述文案只在 `notes_for_user` / `post_notes` 出现一次 |
| ETag / 条件请求 | 清单带 `ETag`，未变更时服务端返回 304，客户端用本地缓存 |

目标：单组件分片 < 50 KB，索引 < 30 KB。**如果某个分片超过 100 KB，说明该拆分了。**

## 4.6 清单的生成与校验（工具链）

清单**不允许手写**，必须由 `tools/` 下的脚本生成（参考实现的硬编码列表就是手写维护腐烂的典型）：

```
tools/
├── probe/          逐个上游探测：目录页 / Release 接口 / 版本索引 JSON
├── resolve/        解析出真实下载地址与文件名（含中转页、防盗链、签名重定向）
├── verify/         实际发起请求校验：HTTP 状态、文件大小、SHA-256
├── gen/            生成 client.json 与 components/*.json，并写入 manifest_sha256
└── publish/        提交到清单仓库（由 CI 执行，见 10）
```

**校验的强制规则**（来自实测）：任何新版本进入清单前必须完成
"**实际下载并算出真实 SHA-256**"或"**至少完成 Range 请求确认大小并记录来源**"。
只做 HEAD 请求是不够的——实测中 HEAD 模式对若干站点会超时误判，
而参考实现正是用 HEAD 请求去"确认版本存在"的。

## 4.7 schema 演进与旧客户端兼容

| 规则 | 说明 |
|---|---|
| `schema` 单调递增 | 每次不兼容变更 +1 |
| **未知字段必须忽略** | 客户端遇到不认识的字段要降级而非崩溃 |
| **未知 `schema` 要降级** | 若 `schema` 高于客户端已知，客户端应尝试按已知字段解析，并在界面标注"部分信息可能无法显示" |
| 双版本并存 | 服务端在过渡期同时保留 `index.json` 与 `index.v2.json` |
| 上报与淘汰 | 客户端可选匿名上报自身版本（默认关闭），用于决定何时停止兼容旧版 |
| 强制升级兜底 | 若旧客户端完全无法解析新清单，用 `min_supported` 强制其升级 |

## 4.8 网络失败时的降级（与参考实现的关键区别）

| 场景 | 行为 |
|---|---|
| 正常 | 带 `If-None-Match` 请求；304 用本地缓存 |
| 网络失败但有本地缓存 | 使用缓存，界面角落标注"资源列表为 x 小时前的快照" |
| 网络失败且无缓存 | 使用**出厂快照**（编译进程序的清单副本），界面**明确标注**："当前离线，正在使用出厂列表，组件版本可能不是最新。" |
| 出厂快照里也没有该组件 | 明确提示"该组件需要联网获取信息"，而不是静默留空 |
| 清单签名校验失败 | **拒绝使用**，回退到缓存/出厂快照，并记 error 日志（这是安全事件，不是普通故障） |

参考实现的实测数据说明了为什么"兜底必须可见"：它的内置兜底列表已经严重过期——
JDK 内置 21 而在线已 27、Node 内置 20.15.0 而在线 26.12.0、Python 内置 3.12.4 而在线 3.16.0——
但它**静默使用、零提示**，用户以为自己装的是最新版。
