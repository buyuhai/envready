# EnvReady 设计文档 00 —— 总览与设计原则

> 本文档是整套设计文档的入口与索引。所有后续文档都必须服从本文档定义的原则与术语。

---

## 0.1 一句话定位

**EnvReady（环境就绪）** 是一个面向零基础学生的桌面程序：学生双击打开，按界面上的说明点几下，
程序自动从官方渠道把编程环境装好、配好、验证好，并用自然语言告诉他"刚才做了什么、装在哪里、
下一步该做什么"。

定位语：**一键之后，环境就绪。**

---

## 0.2 目标用户与真实场景

设计必须以真实场景为准，而不是以"会用电脑的人"为准。

**主要用户：大一新生，第一次学编程。**

他们的真实处境（这些处境直接决定设计取舍）：

| 处境 | 对设计的要求 |
|---|---|
| 不知道"环境变量""PATH""编译器"是什么 | 界面上的词必须是日常用语；专业词只在"查看详情"里出现 |
| 用的是自己的笔记本，没有管理员权限（或不敢点 UAC） | 全部安装到用户目录，全程不需要管理员 |
| 在宿舍/机房网络，可能有代理、可能限速、可能深夜断网 | 下载必须可续传、可换源、可离线包安装 |
| 出问题身边没人可问，只能在百度/抖音里搜 | 报错必须自己解释清楚"哪里错了、你可以怎么办" |
| 装坏了会连带影响整个电脑（环境变量一改错，命令行全废） | 任何环境改动都要可回滚、要备份 |
| 会同时装上好几个语言（课程需要 C、Python、Java） | 多版本共存与切换要能管住，不能互相踩 |
| 耐心有限，看到黑色窗口和英文报错就放弃 | 不用命令行做任何必需操作；失败要有明确出路 |

**次要用户：助教/老师。** 他们需要的是"告诉学生装这个"，而不是自己去帮每个人装。因此后续版本可考虑
"导出环境清单 / 一键复现某个环境"的能力（本期不做，但清单格式要为此留出空间）。

## 0.3 设计原则

### 原则一：过程可解释（Explainable）

用户随时能回答三个问题：**正在做什么、为什么做、做完之后我该干什么。**

具体要求：

1. 每一个耗时超过 2 秒的动作，界面上都有对应的一句话说明（不能只有转圈）。
2. 不允许出现裸技术词。术语必须经过"人话映射表"（见 `08-面向新手的交互规范.md`）。
3. 每一步完成后给出**可自行验证的检查方式**（例如"打开一个新的命令行窗口，输入 `gcc --version`，
   应该看到 `gcc (MinGW-W64 ...) 14.2.0`"）。
4. 需要用户自己做的事（例如数据库要初始化、某软件要登录）必须在**界面上醒目展示**，
   不能只写进日志（这是参考实现 murig 的实际缺陷：`post_notes` 定义了、也渲染了，
   但只打印在底部日志窗的 warn 行里，用户看不到）。

### 原则二：可回滚（Reversible）

**任何人机都做不到"永不失败"，所以失败必须能退回去。**

1. 改动环境变量前，先备份旧值到磁盘（带时间戳，可列出、可一键还原）。
2. 写入操作幂等：重复执行不产生重复条目。
3. 组件安装先落到临时目录，校验通过再原子改名到最终位置。
4. 程序自身更新采用"版本目录 + 指针"，失败自动回退到上一个可用版本。
5. 提供"卸载 / 重置 / 修复"入口，且卸载要把自己写过的环境变量清理干净。

### 原则三：没有静默失败（No Silent Failure）

这是参考实现最严重的一类问题，必须从语言和架构两层防住。

1. **语言层**：Go 的 `if err != nil` 强制面对每个错误；禁止 `_ = err`（需忽略时必须写明原因并记日志）。
2. **架构层**：任何"部分成功"都必须在界面上体现为"部分成功"，不能显示成成功。
   - 装完了但自检没通过 → 显示"已安装，但自检未通过"，并给出下一步。
   - 在线清单拉取失败退到出厂快照 → 界面必须标注"当前离线，使用出厂列表，版本可能不是最新"。
3. **兜底不等于静默**：可以用旧数据继续，但必须让用户知道用的是旧数据。
4. **异常不许直接抛给用户**：任何内部错误都要经过"错误分类 → 人话模板 → 用户可以怎么做"这条流水线。

### 原则四：绝不越过的一条线

**无论如何不能把用户电脑弄坏，也不能让用户的环境比安装前更差。**

具体含义：

- 修改任何系统级设置（用户级 PATH、shell 配置）之前必须有备份，且备份必须先落盘再改。
- 不删除任何不属于本程序的文件。
- 不修改系统的机器级环境变量（`HKLM`），只动用户级（`HKCU`）与用户自己的 shell 配置。
- 卸载 `<ENV_ROOT>` 之外的任何目录都必须先问用户。
- 用户自己装的 JDK/Python（我们没装过的）只做检测与提示，绝不擅自改动。

## 0.4 相对参考实现 murig 的差异

参考实现 `murig`（原 `env-auto-setup`）是我们最重要的对照组：它验证了"一站式装配"这条路可行，
同时它的缺陷就是我们这份设计的清单来源。完整缺陷分析见 `D:\work place\murig-analysis\REPORT.md`
（35 项，S1–S35）与 `D:\work place\murig-analysis\VERIFY.md`（下载链路实测）。

| 维度 | murig 的做法 | EnvReady 的做法 | 依据 |
|---|---|---|---|
| 架构 | Python + PySide6 单文件 4,315 行 | Go + Wails，按职责分包 | 可维护性；自更新几乎无法用单文件实现 |
| 分发体积 | PyInstaller 打包，100 MB 以上，杀软误报重灾区 | Go 静态编译，约 15–20 MB | 机房网络下"下载即被拦"等于失败 |
| 更新 | 无自更新，只能重新下载整包 | 启动器 + 版本目录 + 指针 + 健康检查自动回退 | 用户要求 + 自更新是本项目研究点 |
| 版本清单 | 硬编码在 `build_components()`，新增组件必须改代码发版 | 云端清单 + 内置出厂快照，改数据即上新组件 | 维护成本 |
| 清单时效 | 兜底列表过期后静默使用（实测 jdk 内置 21、在线已 27） | 兜底必须可见、可解释 | 原则三 |
| 下载 | 单源、无校验和、无断点续传、失败从头再来 | 多镜像测速择优 + 校验和 + 续传 + 代理 | 实测 218 条直链中 26 条异常 |
| 安装结果验证 | 进度条到 100% 即算成功 | 装完必须跑自检命令并核对版本号 | 原则一、三 |
| 环境变量（Windows） | 先 `winreg` 写注册表，又紧跟 `setx` 覆盖（README 声称规避 1024 限制，实际自相矛盾）；无 `WM_SETTINGCHANGE` 广播 | 只走注册表 API，保持 `REG_EXPAND_SZ` 类型，写后广播 + 回读校验 | murig 缺陷 S1/S2 |
| 环境变量（Unix） | 每条 PATH 一个 marker，只增不减，换版本后旧路径仍在且排在前面（装新版跑旧版） | 按组件归组管理，切换版本时成对替换 | murig 缺陷 S7 |
| 备份与回滚 | 无 | 写前备份 + 一键还原 | 原则二 |
| 报错 | 把 Python 调用栈直接打印进日志窗 | 错误分类 + 人话说明 + 建议动作 | 原则一 |
| 卸载 | 无卸载、无重置入口 | 卸载/重置/修复 | 原则二 |

## 0.5 术语表（代码与界面文案的统一叫法）

| 术语 | 含义 | 界面上对用户怎么说 |
|---|---|---|
| **程序根 / APP_ROOT** | EnvReady 自己的目录（启动器、各版本主程序、日志、缓存） | 不出现（"查看详情"里可看到路径） |
| **环境根 / ENV_ROOT** | 学生装的编程环境所在目录，是用户资产 | "你的编程环境保存在这里" |
| **组件 / Component** | 一个可安装的软件单元，如"Python 3.12"、"MinGW-w64" | "Python"、"C/C++ 编译器" |
| **组件 key** | 组件的稳定标识，如 `python`、`mingw` | 不出现 |
| **环境 / Environment** | 一组组件的集合，构成"能写 Python 程序的机器状态" | "你的 Python 环境" |
| **清单 / Manifest** | 描述"有哪些组件、有哪些版本、从哪里下载、怎么校验"的 JSON | 不出现（或"资源列表"） |
| **出厂快照** | 编译进程序的清单副本，联网失败时使用 | "出厂列表（可能不是最新）" |
| **指针 / Pointer** | `current.json`，记录当前该启动哪个版本的程序、状态如何 | 不出现 |
| **启动器 / Launcher** | 极小程序，读指针、启动对应版本、必要时回退 | 不出现（用户看到的就是程序图标） |
| **健康标记 / Health Marker** | 新版启动成功时写的凭据文件 | 不出现 |
| **自检 / Verify** | 安装完成后实际运行命令确认可用 | "正在检查是否安装成功" |
| **信任根** | 硬编码在程序里的公钥，是整条校验链的起点 | 不出现 |
| **人话映射** | 把技术表述转换成学生能懂的说法 | 见 `08` |

## 0.7 本设计明确"不做"的事

写下不做的事，防止范围失控：

1. **不做包管理器。** 我们不做依赖求解、不做版本冲突计算（那是 conda/pip/npm 的事）。
   我们只做"把工具链装到正确位置 + 配好环境变量 + 验证可用"。
2. **不托管任何安装包。** 程序本体开源托管在 GitHub；**所有下载资源一律直取官方渠道**
   （官方站、官方镜像、官方 Release），我们不中转、不缓存、不二次分发，
   因此不承担再分发的合规责任。
3. **不做账号体系。** 不需要登录、不收集个人信息。可选匿名统计（仅客户端版本号）默认关闭。
4. **不做在线 IDE、不做代码托管。** 学生的代码在他自己电脑上。
5. **不承诺覆盖所有语言。** 首期目标是"不少于 5 类环境（含 C/C++）跑通且成功率 ≥ 90%"，
   而不是"支持 29 个组件"。广度是后续的事。
6. **不做静默安装。** 任何需要管理员权限的安装（某些数据库的 Windows 安装器）一律明确告知用户
   并让其自己决定，我们不尝试绕过 UAC。
