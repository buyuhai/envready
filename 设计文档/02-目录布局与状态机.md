# EnvReady 设计文档 02 —— 目录布局、状态机与崩溃恢复

> 本文档定义"东西放在哪、当前处于什么状态、中途崩了怎么办"。这是整个程序可靠性的地基：
> 只要这一层是对的，任何上层操作都可以重试；这一层错了，再好的界面也救不回来。

---

## 2.1 两类目录必须严格分开

| | 程序根 APP_ROOT | 环境根 ENV_ROOT |
|---|---|---|
| 装的是什么 | EnvReady 自己（启动器、各版本主程序、日志、下载缓存） | 学生装的编程环境（MinGW、Python、JDK…） |
| 谁拥有 | 本程序 | **用户** |
| 更新时会怎样 | 整体切换版本目录，旧版本可被清理 | **绝不触碰**（不迁移、不重装、不清理） |
| 卸载时会怎样 | 删除 | 询问用户后决定保留或删除 |
| 可迁移性 | 不需要迁移 | 允许用户改到别的盘 |

**红线：更新器的可写范围只允许在 APP_ROOT 内。** 更新代码如果出现对 ENV_ROOT 的写操作，
一律视为缺陷。

---

## 2.2 三平台路径

| 用途 | Windows | macOS | Linux |
|---|---|---|---|
| APP_ROOT | `%LOCALAPPDATA%\EnvReady\` | `~/Library/Application Support/EnvReady/` | `${XDG_DATA_HOME:-~/.local/share}/envready/` |
| 启动器 | `<APP_ROOT>\EnvReady.exe` | `<APP_ROOT>/EnvReady` | `<APP_ROOT>/envready` |
| 指针 | `<APP_ROOT>\current.json` | 同 | 同 |
| 版本目录 | `<APP_ROOT>\app\<版本>\` | 同 | 同 |
| 下载缓存 | `<APP_ROOT>\downloads\` | 同 | 同 |
| 日志 | `<APP_ROOT>\logs\` | 同 | 同 |
| 锁 | `<APP_ROOT>\.lock` | 同 | 同 |
| ENV_ROOT 默认值 | `%LOCALAPPDATA%\EnvReady\envs\` | `~/EnvReady/envs/` | `<APP_ROOT>/envs/` |
| ENV_ROOT 用户可改到 | 任意可写盘（如 `D:\DevEnv`） | 任意 | 任意 |

**为什么用 `%LOCALAPPDATA%` 而不是 `Program Files`：**
不需要管理员权限，符合"免管理员"的核心定位；同时它是用户级目录，更新时不会被系统保护阻断。
代价是"看起来不像正式安装的软件"，这由界面上的"你的环境装在这里"来弥补。

**为什么 ENV_ROOT 不放在 APP_ROOT 里而默认放外面：**
默认值虽然落在 APP_ROOT 下（同一磁盘、好找），但**设为可独立配置**，
这样学生可以把环境放到 D 盘（机房机器 C 盘常满），而程序更新不影响它。

## 2.3 目录结构与生命周期

```
<APP_ROOT>/
├── EnvReady.exe            启动器：读指针 → 拉起主程序 → 视状态决定是否驻留观察
├── current.json            指针：唯一真值来源，原子写
├── app/
│   ├── 1.0.0/              已发布过的版本目录（内含 EnvReady-main 与前端资源）
│   ├── 1.1.0/
│   ├── 1.1.1.tmp-a3f1/     正在解压的临时目录（启动时按需清理）
│   └── 1.1.0.broken-20261016T1022/   已判定失败的版本，保留供诊断
├── downloads/
│   ├── envready-1.1.1.zip          下载完成的包
│   └── envready-1.1.1.zip.part     未完成的分片
├── logs/
│   ├── launcher-20261016.log       启动器日志（它常驻时间极短，但必须留证）
│   └── app-20261016.log
└── .lock
```

| 条目 | 何时创建 | 何时删除 | 谁负责 |
|---|---|---|---|
| `app/<版本>/` | 更新或首次安装，校验通过后原子改名 | GC（保留最近 2 个历史版本） | `internal/update` |
| `app/*.tmp-*/` | 解压开始时 | 解压成功改名后；**异常退出后由下次启动清理** | `internal/update` |
| `app/*.broken-*/` | 回退时改名 | 用户主动"清理旧版本"或 GC 只保留 1 个样本 | `internal/update` |
| `downloads/*.part` | 下载开始时 | 下载完成改名后；校验失败时删除 | `internal/download` |
| `current.json.tmp` | 写指针时 | rename 后即消失；残留则由下次启动删除 | `internal/update` |

## 2.4 指针文件与状态机

### 2.4.1 结构

```json
{
  "schema": 1,
  "version": "1.1.0",
  "state": "pending",
  "prev": "1.0.0",
  "attempts": 1,
  "nonce": "a3f1c8e2...",
  "updated_at": "2026-10-16T10:22:31Z"
}
```

### 2.4.2 三个状态与转移

| 当前状态 | 触发事件 | 新状态 | 说明 |
|---|---|---|---|
| （无指针） | 首次安装完成 | `pending` | 与更新后行为一致，统一走一遍健康检查 |
| `stable` | 检测到新版本并就位 | `pending`（`prev`=当前版本） | 这时还不切换实际运行版本？—— 见下 |
| `pending` | 健康检查通过（stage 2 + nonce 匹配） | `stable` | 清空 `attempts`、清除健康标记 |
| `pending` | 健康检查失败且 `attempts` 未达上限 | `pending`（`attempts+1`） | 再给一次机会（应对冷启动慢） |
| `pending` | 健康检查失败且已达上限 | `stable`（`version`=`prev`） | 回退；失败目录改名 `.broken-<时间戳>` |
| `stable` | 主程序在运行中崩溃（连续 3 次异常退出） | `stable` 但标记 `suspect` | 下次启动提示"上次好像异常退出"，并给"回到上一个版本"的选项 |

**关于"何时真正切换版本"的一个重要设计选择：**

采用**先切换指针、再启动新版**（而不是"先启动新版试试、成功再切指针"），原因：
启动器读指针决定启动哪个版本，如果指针没切，启动器就不知道该启动新版，
需要额外参数传递"临时试启动"的信息，复杂度更高。

为了保证安全性，切换指针时**同时写入 `prev`**，一旦新版启动失败，指针可以直接改回 `prev`。
换句话说：**试错的代价只是"改一次指针"，而不是"重装一遍"。**

### 2.4.3 指针写入协议（必须原子）

1. 写 `current.json.tmp`（写入完整 JSON，含 `fsync`）。
2. `rename` 覆盖 `current.json`（同目录内 rename 在三平台上都是原子的）。
3. 若第 1 步后进程被杀：临时文件残留，不影响旧指针，下次启动清理。

**绝不**采用"打开 `current.json` 直接覆写"的方式——那样在两次写入之间断电会得到半个 JSON。

## 2.5 启动器流程

```
读 current.json
│
├─ 文件不存在 / JSON 解析失败 / 指向的目录或主程序不存在
│     → 修复模式（见 2.6）
│
├─ state = stable
│     → 启动 app/<version>/，启动器立即退出
│
└─ state = pending
      → 生成 nonce，以环境变量 ENVREADY_HANDSHAKE=<nonce> 启动主程序
      → 驻留观察最多 N 秒（默认 30 秒）
      → 判定成功 / 失败 / 重试（见 03-更新机制）
```

`stable` 是日常路径（99% 的启动）：一次 JSON 读取 + 一次进程创建，然后启动器退出。
不常驻是有意的——**不常驻的进程才能被安全替换**，这样启动器自身的更新不需要任何
"自我改名 / 空壳进程" 的技巧。

## 2.6 修复模式（启动器无法找到可用版本时）

触发条件：指针缺失、损坏、或指向的版本目录已不存在/主程序文件缺失。

处理顺序：

1. 扫描 `app/` 下所有目录（排除 `.tmp-*`、`.broken-*`）。
2. 对每个候选做**最小校验**：主程序文件存在 + 文件大小与清单/hash 记录相符（若记录可用）。
3. 按版本号从高到低选第一个可用者，写回指针（`state=stable`），并记日志。
4. 若一个都不可用：
   - 若本地存在 `downloads/` 里已下载好的安装包 → 提示用户"程序文件丢失，正在重新安装"并自动重装。
   - 否则 → 弹出**启动器自带的极简对话框**（不依赖主程序、不依赖 WebView）：
     "EnvReady 的程序文件不完整，需要重新下载安装。"
     给出"打开下载页面"按钮（打开浏览器）+ "复制下载地址"按钮 + 退出。
     **启动器必须能独立显示这个对话框**，这是它不能依赖主程序的原因。

## 2.7 首次安装流程

与更新流程共用同一套机制，避免两套代码（两套代码必然有一套先腐烂）：

1. 用户在浏览器/下载页得到 `envready-<版本>-<平台>.zip`，解压后运行启动器。
2. 启动器发现无指针 → 进入"首次初始化"：
   a. 确认 APP_ROOT 可写（不可写则提示换位置，见 2.8）。
   b. 把当前目录解析为版本目录，**先校验自己的完整性**（与随包发布的清单核对每个文件哈希）。
   c. 校验通过 → 把程序文件移动到 `app/<版本>/`，写指针 `state=stable`。
      （首次安装没有"旧版本"可回退，因此不需要 pending 观察；但若移动后启动失败，
        会落到修复模式。）
   d. 校验失败 → 明确告知"安装包可能下载不完整，请重新下载"，不写指针，不留下半成品。
3. 首次运行时由主程序做一次"环境体检"：检查磁盘空间、是否已有其他语言的 SDK、
   是否缺 WebView2（Windows），并把结果用人话展示。

## 2.8 可写性与空间预检

启动器在启动主程序前必须完成（耗时可忽略，但能避免大量后期失败）：

| 检查 | 不通过的后果 | 处理 |
|---|---|---|
| APP_ROOT 可写 | 更新必然失败（这是最常见的"更新没反应"原因） | 明确提示并把可写性诊断写进日志 |
| APP_ROOT 剩余空间 ≥ 200 MB | 解压中断 | 提示清理，给出"查看占用"入口 |
| ENV_ROOT 可写（若已配置） | 组件安装失败 | 提示重新选择环境目录 |
| 环境目录所在盘剩余空间 ≥ 组件需求 × 1.5 | 大组件（实测有单包 1.8 GB）下载或解压失败 | 在开始下载前就提示，而不是下到一半才失败 |

**"在开始之前失败"远好于"做到一半失败"**，这是我们与参考实现最重要的体验差异之一。

## 2.9 版本目录的保留与清理（GC）

- **保留策略**：当前版本 + 最近 2 个历史版本 + 1 个 `.broken-` 样本。
- **执行时机**：**启动成功之后**，后台低优先级执行；绝不在启动前执行
  （清理失败会阻塞启动，而启动是用户唯一真正关心的事）。
- **失败处理**：清理失败只记日志，不提示用户。
- **空间上限**：所有历史版本合计超过 500 MB 时，多清理一个最旧的。
- **永不清理**：`<ENV_ROOT>`、`downloads/` 里正在被使用的文件、`logs/` 中未过期的日志。

## 2.10 锁与并发

| 锁 | 文件/对象 | 作用 | 持有时间 |
|---|---|---|---|
| 实例锁 | Windows：命名互斥体；Unix：`<APP_ROOT>/.lock` 的 `flock` | 防止双击打开两个窗口、两个更新器同时动作 | 进程生命周期 |
| 更新锁 | `<APP_ROOT>/.update.lock`（内容含 PID + 时间戳 + 动作） | 保护指针写入与启动器替换 | 极短（秒级） |

- 第二实例的行为：不是简单报错，而是**唤起已有窗口**（Windows 用窗口消息，Unix 用信号/文件），
  这样"用户以为没打开、又点了一次"不会有两个程序同时改环境变量。
- **陈旧锁判定**：锁内 PID 不存在，或时间戳超过 10 分钟 → 视为陈旧锁，接管并记 `warn`。
  绝不能死等——一次崩溃就会让程序永久打不开，这是最严重的可用性事故。

## 2.11 崩溃恢复矩阵

**这张表必须逐行变成自动化测试用例**（见 `13-测试与验收.md` 的故障注入部分）。
测试方式：在指定位置强制结束进程，然后重启，断言最终状态符合"期望结果"列。

| # | 崩溃点 | 磁盘残留状态 | 下次启动的期望行为 |
|---|---|---|---|
| 1 | 下载中 | `downloads/x.zip.part` + 续传元数据 | 校验和/ETag 未变 → 续传；否则删除重下 |
| 2 | 下载完成、校验和失败 | `x.zip` | 删除 `x.zip` 与 `.part`，静默重试一次；再失败则放弃本次更新（不打扰用户） |
| 3 | 解压中 | `app/1.1.0.tmp-xxxx/` | 清理所有 `.tmp-*` 目录，重新解压 |
| 4 | 解压完成、rename 前 | 同上 | 同上（重新解压成本可接受） |
| 5 | rename 后、写指针前 | `app/1.1.0/` 已就位，指针仍指 1.0.0 | 识别为"已就绪未启用"，下次可直接写指针启用 |
| 6 | 写指针中 | `current.json.tmp` 残留 | 删除临时文件，使用旧指针（旧指针未被破坏） |
| 7 | 指针已切换、主程序尚未启动 | `state=pending` | 正常进入观察流程 |
| 8 | 观察中崩溃 | `state=pending`，可能残留健康标记 | 同上，`attempts` 累加（缺 `prev` 时应退到修复模式） |
| 9 | 回退动作中崩溃 | 可能仍为 `pending`，`broken-` 目录可能已改名 | 重试回退；broken 目录名带时间戳，重试不会冲突（幂等） |
| 10 | 替换启动器时崩溃 | `EnvReady.exe.new` 残留 | 启动器启动时发现 `.new` 且自身校验通过 → 完成替换并记日志 |
| 11 | 启动器自身损坏 | 无法启动 | 最后兜底：引导用户重新下载完整安装包 |
| 12 | 组件解压到一半断电 | `<ENV_ROOT>/<组件>/.stage-<版本>/` | 启动时清理 stage 目录；已装好的旧版本不受影响 |
| 13 | 环境变量写入一半断电 | 备份文件已存在，注册表可能未改或已改 | 启动时比对"当前值 vs 备份"与"记录的目标值"，报告并让用户选择"完成写入 / 还原备份" |

第 13 条是本项目特有且最容易被忽略的：环境变量不是"要么全写要么全不写"，
Windows 注册表写入是原子的（单值），但"写 `JAVA_HOME` + 追加 `PATH`"是两个值，
中间断电会得到"变量设了但 PATH 没加"的半成品状态。因此**每一次环境改动都要留一条
"意图记录"**（想改成什么样），启动时才能判定并修复。
