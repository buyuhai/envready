# EnvReady 设计文档 07 —— 环境变量管理

> 这是全项目**风险最高**的模块：装不上顶多重试，环境变量写错会让学生的整台电脑命令行不可用。
> 因此本文档的每一条都围绕"可回滚、幂等、可解释"。
> 参考实现（murig）在这一层的实测缺陷最多（S1–S7 等），逐条都有对应设计。

---

## 7.1 目标与红线

**目标**：让用户装的组件在**新开的**命令行窗口里可用，并在用户换版本/卸载时保持干净。

| 红线 | 说明 |
|---|---|
| 只动用户级 | Windows 只用 `HKCU\Environment`；**绝不写 `HKLM`**（系统级 PATH） |
| 改前必备份 | 备份必须先落盘成功，才开始修改 |
| 幂等 | 重复执行不产生重复条目、不产生重复配置块 |
| 可回读校验 | 写完立刻读回比对，不一致立即报告（不能"以为写成功了"） |
| 只清理自己写的 | 卸载时只移除本程序添加的内容，用户自己加的路径一律不动 |
| 不破坏他人配置 | 修改 shell 配置文件时保留注释、缩进、换行风格；不重排用户已有内容 |

## 7.2 Windows 协议（注册表）

### 7.2.1 为什么不使用 `setx`

- `setx` 会把值截断（历史上限 1024 字符），长 PATH 会被静默截短——这是**破坏性**的。
- `setx` 写的是注册表但走的是另一条代码路径，无法控制值类型（`REG_SZ` / `REG_EXPAND_SZ`）。
- 参考实现的做法自相矛盾：它先用自己的注册表写入，**紧接着又调了一次 `setx` 覆盖同一个值**，
  README 声称"规避 setx 的 1024 限制"，实际上截断风险依然存在。这是必须避免的重复写入。

**结论：只用注册表 API 读写，一次写入，不做二次覆盖。**

### 7.2.2 写入规则

| 项 | 规则 |
|---|---|
| 键 | `HKEY_CURRENT_USER\Environment` |
| 值类型 | 若值中包含 `%`（如 `%USERPROFILE%`、`%LOCALAPPDATA%`）→ `REG_EXPAND_SZ`；否则 `REG_SZ` |
| 读取 | 必须用**不展开环境变量**的方式读取原始值（`DoNotExpandEnvironmentNames`），同时读取值类型；否则回写时会把 `%USERPROFILE%` 变成硬编码路径，破坏用户的原有配置 |
| 组件首页变量 | 形如 `JAVA_HOME` / `PYTHON_HOME`：直接 `SetValue`（覆盖），旧值先备份 |
| PATH | 特殊处理见 7.2.3 |

### 7.2.3 PATH 的读写

```
读：取原始字符串 → 按 ; 切分 → 去空项 → 得到有序列表
写：把目标项与现有列表逐项比较（归一化后比较，见下）
    已存在 → 不重复添加（幂等）
    不存在 → 插入（默认插到最前，见 7.5 的顺序策略）
    写回时用 ; 连接，保持原有条目的相对顺序
```

**比较必须归一化**，否则会出现重复项（参考实现的比较是纯字符串比较，不做归一化）：

- Windows 路径比较**不区分大小写**。
- 去掉末尾的 `\`（`C:\tools\` 与 `C:\tools` 视为同一条）。
- 统一分隔符（`/` 与 `\` 视为等价）。
- 比较时展开 `%VAR%`，但**存储时保留原始形式**。

### 7.2.4 写后必须广播

写完注册表后，必须调用：

```
SendMessageTimeout(HWND_BROADCAST, WM_SETTINGCHANGE, 0, "Environment", SMTO_ABORTIFHUNG, 5000ms)
```

**为什么必须有**：由资源管理器（开始菜单、桌面快捷方式）启动的程序（例如 VS Code）
是从 Explorer 继承环境的；不广播，这些程序在用户注销/重启前都看不到新变量。
参考实现只留了一句"通知系统刷新"的注释，**实际没有任何广播代码**，
于是 README 里"新开终端即可"的说法并不总成立。

**广播的局限必须向用户说明**（写进文案）：
- 已经在运行的终端/编辑器**不会**自动获得新变量，必须重启它们。
- 广播可能被安全软件拦截，因此还要教用户"如果新窗口里还看不到，就重启一次电脑"。

### 7.2.5 回读校验

写完后立即重新读取该值，与期望值逐项比对；不一致 → 视为失败，
报告"环境变量写入后校验不一致"，并保留备份供还原。

## 7.3 Unix 协议（shell 配置文件）

### 7.3.1 先确定"用户的登录 shell"，不能只信 `$SHELL`

参考实现用 `os.environ.get("SHELL")` 判断，问题是：**从 Finder / Dock / 桌面图标启动的
图形程序，`$SHELL` 可能为空**，于是它落到 `~/.profile`，而 zsh 用户根本不会读这个文件，
配置写了等于没写。

正确顺序：

1. 从系统账号数据库读取登录 shell：
   - macOS：`dscl . -read /Users/<user> UserShell`
   - Linux：解析 `/etc/passwd`（Go 可用系统调用或直接读该文件）
2. 读取失败 → 用 `$SHELL`（在终端里启动时有效）
3. 仍不确定 → 用平台默认（macOS 自 Catalina 起为 `/bin/zsh`；Linux 为 `/bin/bash`）
4. **若推导结果与 `$SHELL` 冲突**，以系统账号数据库为准，并在日志中记录该冲突。

### 7.3.2 每种 shell 写哪个文件、用什么语法

| shell | 文件 | 语法 | 说明 |
|---|---|---|---|
| zsh | `~/.zshrc` | `export X="…"` | macOS 默认；终端启动时会读 |
| bash (macOS) | `~/.bash_profile` | `export X="…"` | macOS 登录 shell 读 `.bash_profile` 而非 `.bashrc` |
| bash (Linux) | `~/.bashrc` | `export X="…"` | 终端模拟器默认启动交互式非登录 shell |
| fish | `~/.config/fish/config.fish` | `set -gx X "…"`；PATH 用 `fish_add_path` 或 `set -gx PATH … $PATH` | **语法完全不同** |
| 其他/未知 | 不写，改为提示 | —— | 见 7.3.5 |

**fish 必须单独处理，不能写 bash 语法**：把 `export X=…` 写进 `config.fish` 会让 fish
在启动时报语法错误，等于弄坏了用户的 shell 配置。这属于"绝不能做"的一类。

### 7.3.3 配置块设计（按组件归组，而不是按路径）

参考实现为**每一个 PATH 条目**单独写一个块，块标记里嵌了完整路径：

```
# >>> env-auto-setup:PATH:{完整路径} >>>
export PATH="{完整路径}:$PATH"
# <<< env-auto-setup:PATH:{完整路径} <<<
```

后果：换版本/换目录后旧块永远残留（因为标记里含路径，找不到旧标记就再追加一个），
PATH 越来越长，且新旧版本混在 PATH 里。

**本项目的块设计：以组件为单位，一个组件一个块，块内包含该组件的所有环境设置。**

```
# >>> EnvReady:mingw >>>
# 由 EnvReady 自动生成，请勿手工修改本块内容
export MINGW_HOME="/Users/alice/EnvReady/envs/mingw/mingw-14.2.0"
export PATH="/Users/alice/EnvReady/envs/mingw/mingw-14.2.0/bin:$PATH"
# <<< EnvReady:mingw <<<
```

规则：

1. **块名只含组件 key**（稳定、与路径和版本无关）→ 换版本时能精确找到并**整块替换**，
   不会残留、不会累积。
2. 替换算法：找到 `begin` 标记 → 找到 `end` 标记 → 用新块替换中间内容（含标记）。
   找不到完整配对 → 不猜，报告异常并让用户选择（而不是追加一个可能重复的块）。
3. 幂等：块存在且内容一致 → 什么都不做并返回"已是最新"。
4. 换行风格沿用文件原有风格（CRLF/LF）；文件末尾确保有换行。
5. 写入前备份原文件到 `<APP_ROOT>/env-backup/`。

### 7.3.4 生效范围必须说明

写入 `~/.zshrc` 之类文件后：

- **新开的终端**会生效。
- 已开的终端需要 `source ~/.zshrc` 或重开。
- 从 Dock 启动的图形程序（VS Code）**可能不会读取** `.zshrc`，
  因此我们额外提供"生成编辑器配置"的能力（见 `09`），不依赖环境变量继承。

文案不能再出现参考实现那种"请执行 `source ~/.zshrc`"的硬编码提示
（它对 bash 用户是错的，对 fish 用户更是错的）——必须**根据实际写入的文件生成提示**。

### 7.3.5 无法确定 shell 时的处理

不写任何文件。改为：

- 在界面上明确告知："我们不认识你的终端配置方式，为了避免弄坏你的配置，
  没有自动修改。你可以参考下面两行内容，自己加到你的配置里。"
- 展示**可直接复制的两行**（按最可能的 shell 给出语法）。
- 同时提供"我用的终端是：zsh / bash / fish / 其他"的选择器，选完后再自动写入。

**宁可让用户手工复制，也不猜着写坏他的配置。**

## 7.4 备份、意图记录与回滚

### 7.4.1 备份

| 平台 | 备份内容 | 位置 |
|---|---|---|
| Windows | 相关注册表值的**原始未展开值**与值类型（含完整 PATH 字符串） | `<APP_ROOT>/env-backup/env-<时间戳>.json` |
| Unix | 被修改文件的完整副本 | `<APP_ROOT>/env-backup/<文件名>-<时间戳>` |

- 备份**先落盘并 fsync**，成功后才开始修改。
- 每次改动都产生一份备份（不覆盖旧备份），保留最近 20 份，超出后删最旧。

### 7.4.2 意图记录（崩溃后可修复）

参考实现没有这一层，于是"设了 `JAVA_HOME`，但追加 PATH 时断电"会留下半成品状态。

设计：在修改前写 `<APP_ROOT>/env-intent.json`：

```json
{
  "operation": "activate",
  "component": "mingw",
  "version": "14.2.0",
  "targets": [
    { "kind": "registry_value", "name": "MINGW_HOME", "new": "…", "old": "…" },
    { "kind": "path_entry",      "value": "…/bin",      "position": "prepend" }
  ],
  "backup_file": "env-backup/env-20261016T1022.json",
  "started_at": "…"
}
```

- 全部成功 → 删除该文件（视为事务提交）。
- 进程启动时若发现该文件存在 → 说明上次改动未完成 →
  比对当前实际值与目标值，给出选择："完成上次的修改" / "还原到修改前"，
  并**在界面上说明发生了什么**（不能静默处理）。
- 这也顺带解决了"用户点了安装但我们崩溃了"的信任问题。

### 7.4.3 一键还原

界面提供"环境变量备份与还原"：

- 列出历史备份（时间、涉及组件、变更摘要）。
- 查看差异（旧值 vs 当前值，逐条显示）。
- 一键还原（还原前把当前值再备份一份，形成可逆链条）。

参考项目 `Install-MinGW.ps1` 已经实现了同类能力（`Backup-UserPath` + `Restore-UserPath`），
其备份格式（带 `---PATH-BELOW---` 标记的文本）可作为兼容参考。

## 7.5 PATH 顺序策略：为什么默认"插到最前"

| 策略 | 效果 | 风险 |
|---|---|---|
| 追加到末尾（append） | 系统自带的同名工具优先 | 用户刚装了新版 `gcc`，终端里跑的却是系统旧版 → "装了没用" |
| **插到最前（prepend，默认）** | 我们装的版本优先 | 若用户自己另有同版本需求，可能被我们"抢"了 |

**默认选择 prepend**，因为"刚装的工具生效"是用户的直接预期；
而参考实现里出现的"装了新版却跑旧版"正是 PATH 顺序混乱的结果。

例外：清单中 `env.path.position` 可指定 `append`（例如某些不应遮蔽系统命令的辅助工具）。

**关键一致性要求**：自检（`verify`）执行时的环境必须与用户新开终端时**语义一致**
（即使用 prepend 语义构造 PATH）。否则会出现"我们自检通过、用户终端里却不是这样"的错位。

## 7.6 多版本共存与版本切换

### 7.6.1 激活记录

```
<ENV_ROOT>/.active.json          ← 每个组件当前"激活"的版本
{ "mingw": "14.2.0", "python": "3.12.10" }
```

环境变量（`XXX_HOME` 与 PATH 条目）**始终指向激活版本**，而不是"最后一次安装的版本"。

### 7.6.2 切换流程

```
用户点击"切换到 13.2.0"
① 检查该版本目录是否已安装；未安装则先安装
② 备份当前环境变量（7.4.1）
③ 写意图记录（7.4.2）
④ 替换环境变量：XXX_HOME 指向新版本目录；PATH 中本组件的条目整条替换为新版本的 bin
   （不是追加！—— 这是参考实现最严重的问题之一）
⑤ 回读校验
⑥ 更新 .active.json
⑦ 清除意图记录
⑧ 告知用户："已切换到 14.2.0。新开的命令行窗口会用新版本；
   已经打开的窗口需要重新打开才会变。"
```

**"整条替换"是核心**：同一组件在 PATH 中永远只有一条记录，指向当前激活版本。
这样无论切换多少次，PATH 都不会累积。

### 7.6.3 检测多个版本时

界面上显示"你装了 2 个版本"，并明确标出**当前生效的是哪一个**，
提供切换按钮。参考实现完全没有版本切换入口，用户只能看到一堆目录。
