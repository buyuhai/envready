# EnvReady 设计文档 10 —— 云端资源仓库与巡检

> 目的：把"下载链接失效"从**用户侧的问题**变成**上游侧的自动修复**。
> 学生遇到链接失效时只会放弃；我们的目标是在他打开程序之前，链接就已经被修好了。
> 对应的申报指标：**上游版本变更后 24 小时内完成清单同步**。

---

## 10.1 仓库划分

| 仓库 | 内容 | 可见性 | 说明 |
|---|---|---|---|
| `envready` | 程序源码、构建脚本、CI | 公开 | 程序本体开源托管（用户明确要求） |
| `envready-dist` | **清单文件 + 签名**（不含任何安装包） | 公开 | 独立仓库，理由见下 |

**为什么清单要独立仓库：**

1. **历史干净**：巡检 CI 每天可能提交多次清单变更；放在主仓库会淹没代码提交历史，
   review 与 `git blame` 都变得困难。
2. **不触发程序构建**：主仓库的 push 会触发打包与发版流水线，而清单变更**不应该**产生新程序版本。
3. **可直接被 CDN 引用**：jsDelivr 等 CDN 可以直接服务 GitHub 仓库的 tag/分支内容，
   天然获得多镜像能力（`03` 的 3.8 已说明为什么不能走 GitHub API）。
4. **体积与生命周期不同**：清单是高频小文件，程序是低频大文件。

**明确不放的东西**：**任何安装包本体**。
项目定位是"替你去官网拿"，不中转、不缓存、不再分发安装包，
因此既不需要存储成本，也不承担再分发的合规责任（Oracle JDK、SQL Server、
达梦、金仓等的许可都禁止随意再分发）。

## 10.2 `envready-dist` 的目录结构

```
envready-dist/
├── stable/
│   ├── client.json                    客户端版本清单
│   └── components/
│       ├── index.json                 组件索引
│       ├── mingw.json
│       ├── python.json
│       ├── java.json
│       ├── node.json
│       └── …
├── beta/                              预留通道（首期不发布）
├── schema/
│   └── v1/*.schema.json               清单的 JSON Schema（供客户端与 CI 双向校验）
└── .github/workflows/
    └── inspect.yml                    定时巡检
```

**版本化方式**：客户端默认拉 `stable/` 的最新内容（走 CDN 的默认分支或 tag）。
需要回滚时，用 Git 回滚清单提交即可——**清单本身就是可回滚的**，这是选择 Git 托管的重要原因。

## 10.3 清单生成流水线

```
① probe    探测上游
           按组件类型选用不同策略：
           - 官方目录页（Apache Archive、python.org/ftp、nodejs.org/dist）
           - 官方版本索引 JSON（nodejs.org/dist/index.json、Adoptium API）
           - 官方 Release 接口（需注意限流；仅在构建期使用，客户端不依赖）
           - 人工维护的"精选版本候选表"（对没有稳定目录页的组件）

② resolve  解析真实下载地址
           - 处理中转页（如 SourceForge 的 interstitial 页面）
           - 处理防盗链（记录所需 Referer 等请求头）
           - 处理重定向到签名地址的情况：清单里存**原始地址**，
             因为签名地址会过期（实测约 1 小时），由客户端在下载时跟随重定向
           - 判定平台/架构（Windows x64/arm64、macOS arm64/x64、Linux x64）

③ verify   实际请求校验
           - 一律用 GET + Range（不用 HEAD：实测多个站点 HEAD 会超时误判）
           - 记录 HTTP 状态、Content-Length、Content-Type
           - 识别"200 + HTML 错误页"这类伪装成功
           - 计算校验和（见 10.4）

④ gen      生成 JSON
           - 写入 sha256、size、expect_files（关键文件清单）
           - 更新 index.json 的 manifest_sha256
           - 用 schema/v1 校验自己生成的文件（生成器与校验器用同一份 schema）

⑤ publish  提交与发布
           - 提交到 envready-dist，按下面的复核规则决定自动提交还是等待人工
           - 由 CI 完成，人只看需要看的 diff
```

**关键原则：清单不允许手写。** 参考实现的组件列表是手写硬编码在源码里的，
实测其内置兜底列表已经严重过期（JDK 内置 21 / 在线 27，Node 内置 20.15.0 / 在线 26.12.0），
却零提示地继续使用。

## 10.4 校验和的计算策略

| 包大小 | 策略 |
|---|---|
| ≤ 100 MB | CI **完整下载并计算 SHA-256**（这是最强保证） |
| 100 MB – 500 MB | 优先采用**上游官方公布的校验和文件**（如 `SHASUMS256.txt`），并对该文件本身做完整性校验；若上游未提供，则完整下载计算 |
| > 500 MB | 记录 `size` + 上游公布的校验和（若有）；若都没有，字段标为 `null` 并在客户端界面明确显示"未提供完整性校验" |

**诚实原则**：`sha256` 为空时，客户端**必须显示"未校验"**，
绝不能假装校验过（参考实现完全没有校验，却也不会告诉用户）。

**例外**：首期接入的组件（MinGW、Python、Java、Node）都在 100 MB 上下，
对应的是"完整下载计算"这条最强路径，因此首期的校验强度是足够的。

## 10.5 巡检频率与 24 小时指标的达成

| 组件类型 | 巡检频率 | 理由 |
|---|---|---|
| 首期 4 类核心组件 | **每 6 小时** | 直接支撑"24 小时内完成同步"的指标（留出 4 倍余量） |
| 其他组件 | 每天一次 | 成本与收益平衡 |
| 已标记为"上游失效"的组件 | 每 3 天一次 | 减少无效请求 |
| 客户端自身版本 | 每次发版时（发布流水线内） | 由发版触发，不需要巡检 |

**为什么用定时巡检而不是上游 webhook**：GitHub 的 Release 事件 webhook 只覆盖 GitHub 上的项目；
我们的上游包括 Apache Archive、python.org、nodejs.org、Adoptium 等，
统一走"定时轮询 + 差异比较"最省事且覆盖面完整。

## 10.6 变更检测与提交策略

巡检任务的输出是"与当前清单的差异"。按差异类型决定处理方式：

| 变更类型 | 处理 | 是否需要人工复核 |
|---|---|---|
| 上游出现更新版本 | 自动加入清单（作为可选版本），**不自动改 `recommended`** | 否 |
| 已有版本的下载地址变更（同版本换地址） | 自动更新地址 + 重新校验 | 否 |
| 已有版本失效（404） | 标记该版本 `unavailable`，从可选列表移除 | 否（但记日志） |
| **`recommended` 需要变更** | **必须人工确认**（改推荐版本会影响所有新用户） | **是** |
| 校验和变化（同版本内容变了） | **必须人工确认**（可能是上游重新打包，也可能是被篡改） | **是** |
| 上游未提供免编译版本（只见源码包） | 标记该平台 `unsupported` + 说明原因 | 是 |
| 某个组件连续 3 次巡检全部失败 | 自动创建 Issue 并 @ 维护者 | 是（通过 Issue 流程） |

**"自动加入、人工改推荐"这条设计是刻意的**：让清单保持新鲜是机器的事，
让几万名学生装到某个版本是我们的事。

## 10.7 防抖动

上游目录页偶发返回不完整内容，会导致清单被"截断"（版本突然消失），
这类抖动一旦发布出去会让学生看到版本列表跳动。因此：

1. **两次一致原则**：任何"版本消失"的变更，必须连续两次巡检都确认才提交。
2. **单调性检查**：清单中的版本集合不允许突然减少超过 30%（超过则视为异常，等待人工）。
3. **最小条数检查**：同一组件的版本数不允许降到 1 以下（除非确实只有一个版本，如达梦）。
4. **地址连通性复查**：提交前对新增/变更的地址做一次实际请求。
5. **schema 校验**：任何不符合 schema 的输出直接拒绝提交（宁可保持旧清单）。

## 10.8 与客户端的契约

| 项 | 约定 |
|---|---|
| 协议 | 纯 HTTPS GET，静态文件；不做 API、不需要认证 |
| 缓存 | 响应带 `ETag`；客户端用条件请求（304 复用本地） |
| 时效标记 | 每个文件含 `updated_at`，客户端用它计算"这份清单是多久以前的" |
| 签名 | 见 `11`；首期为 `null`，客户端要能处理"无签名"与"签名无效"两种情况（后者拒绝使用） |
| 兼容 | `schema` 版本 + "未知字段忽略" + 过渡期双版本（见 `04` 的 4.7） |
| 体积 | 单分片 < 50 KB、索引 < 30 KB（超限即说明该拆分） |
| 可用性 | 至少两个独立来源（GitHub 原始地址 + CDN），客户端测速择优 |

## 10.9 告警与可观测性

| 指标 | 阈值 | 动作 |
|---|---|---|
| 巡检任务失败 | 连续 2 次 | 创建 Issue |
| 某组件全部版本失效 | 立即 | 创建 Issue + 在清单中标记 `supported: false`，客户端界面显示"暂时不可用（正在修复）" |
| 客户端下载失败率 | 需要客户端上报，首期默认关闭 | 后续版本启用 |
| 清单拉取失败率 | 同上 | —— |
| CI 配额 | GitHub Actions 免费额度 | 逐组件巡检是并行的，注意大文件下载流量 |

**成本控制**：巡检的主要成本是"完整下载算哈希"的流量。
首期 4 类组件合计约 500 MB/次，每天 4 次 = 2 GB/天，在免费额度内可接受。
接入大体积组件（如 1.8 GB 的包）时，必须改用上游公布的校验和，否则成本会失控。

## 10.10 发布流程（人工部分）

```
巡检自动提交（清单）
   ↓
人工复核门禁（仅下列情况需要人看）：
   · recommended 变更
   · 校验和变更
   · 组件被标记为不可用
   ↓
合并 → CDN 自动生效 → 客户端最迟 24 小时内感知
   ↓
出现问题时：git revert 清单提交（分钟级回滚，不影响已装好的用户环境）
```

**重要性质**：清单回滚**永远不会影响用户的已装环境**。
清单只决定"以后能装什么"，不决定"已经装了什么"——
这是把数据与状态分离带来的直接好处，也是相对参考实现（硬编码在程序里，
改错就得发新版本）的实质改进。
