# EnvReady 设计文档 06 —— 下载引擎

> 下载引擎要为三类流量服务：**清单**（小、频繁）、**组件包**（大、偶发，实测最大 1.8 GB）、
> **程序自身更新包**（中，偶发）。三者共用同一套引擎，
> 这样"给学生用的下载"与"给自己更新"共享同一批已修好的缺陷。
> 参考实现的下载实现只有 46 行：单源 `requests.get(stream=True)`、无校验和、
> 无断点续传、失败从头开始、`timeout=30` 只能算整体超时。

---

## 6.1 真实约束（设计依据）

| 约束 | 来源 | 设计要求 |
|---|---|---|
| 校园网/宿舍网存在代理、认证、限速 | 真实场景 | 支持系统代理与环境变量代理；失败时能提示"可能需要在设置里填代理" |
| 断网常见（熄灯断网、掉线） | 真实场景 | 断点续传必须是默认能力，不是附加功能 |
| 上游会给出**带签名的临时地址** | 实测：Adoptium 的 JDK 最新版地址 302 到 `release-assets.githubusercontent.com`，URL 带 `se=` 过期时间，约 1 小时有效 | 长期下载任务必须在**签名过期后能重新解析一次新地址**并继续（或明确告知需要重新开始） |
| 上游有防盗链 | 实测：某信创数据库的 OSS 需要 `Referer` | 清单中支持每平台自定义请求头 |
| 单包极大 | 实测：ollama Windows 包 1792.7 MB、达梦 Linux 794.4 MB、Hadoop 三平台各 696.3 MB | 必须有空间预检、进度、速度、剩余时间、可取消 |
| HEAD 请求不可靠 | 实测：多个站点对 HEAD 超时，而 GET + Range 正常 | **探测与下载一律用 GET + `Range: bytes=0-0`**，不用 HEAD |

---

## 6.2 多镜像测速择优

清单里每个包都带 `mirrors`（前缀列表）。引擎的选源流程：

```
① 若本次会话已有该镜像的测速记录（缓存 10 分钟），直接用最快的
② 否则并发对每个镜像发起 Range: bytes=0-0 探测（超时 5 秒）
③ 记录：是否可用、首字节耗时、是否支持 Range（响应含 Content-Range 才算）
④ 选"可用且支持 Range 中首字节最快"的镜像
⑤ 下载过程中若该镜像连续失败 N 次 → 从候选列表剔除，换下一个（不重新从零开始，若支持 Range）
```

**判定可用性时不要只看到 HTTP 200**：实测多个站点会返回 200 + 一个"未找到"的 HTML 页面。
因此探测要额外检查响应类型与内容特征（例如 `Content-Type` 或前若干字节的魔术字节），
把"HTML 冒充成功"识别为失败。这一条是实测踩过的坑。

## 6.3 下载落盘协议

```
downloads/
├── <file>.part            正在下载的数据
├── <file>.part.meta       续传元数据（JSON）
└── <file>                 完成并通过校验后的最终文件
```

`.part.meta` 内容：

```json
{
  "url": "最终被重定向到的真实 URL",
  "source_prefix": "使用的镜像前缀",
  "etag": "…",
  "last_modified": "…",
  "total_size": 112000000,
  "downloaded": 48123456,
  "sha256_expected": "…",
  "started_at": "…",
  "updated_at": "…"
}
```

流程：

1. 若存在 `.part` + `.part.meta`，且 `url` 与 `etag`/`last_modified` 与服务端当前一致 →
   带 `Range: bytes=<downloaded>-` 续传。
2. 服务端返回 `206 Partial Content` → 追加写入（校验响应里的 `Content-Range` 起点与本地一致）。
3. 服务端返回 `200 OK`（不支持 Range 或资源已变）→ **丢弃已有分片，从头下载**，并提示用户
   "下载服务器不支持续传，正在重新开始"（不能让用户以为在续传却没动）。
4. `downloaded == total_size` → 流式算出的 SHA-256 与清单比对 → 通过则改名去掉 `.part`，
   删除 `.meta`；不通过则删除两者并按错误分类处理。
5. **磁盘空间在开始前检查**：需求 = 包大小 + 解压后预估大小（清单可给 `extracted_size`），
   并留 20% 余量。空间不足时**在下载前**就报错，而不是下到 90% 才失败。

---

## 6.4 断点续传的边界情况

| 情况 | 处理 |
|---|---|
| 服务端不支持 `Range`（返回 200） | 从头开始，并明确提示（见上） |
| 签名地址已过期（403/404） | 用清单中的**原始地址**重新解析一次重定向，拿到新的签名地址；分片保留，用新地址续传 |
| `ETag` 变化（文件被上游替换） | 丢弃分片从头开始（内容已不同，续传会产生损坏文件） |
| 服务端返回的 `Content-Range` 起点与本地分片长度不一致 | 视为不可续传，从头开始 |
| 分片文件本身损坏（进程被杀时最后一块可能不完整） | 写入前先 `fsync` 到分片长度记录点；启动时以 `meta.downloaded` 为准截断到该长度 |
| 同一文件并发下载（例如两个窗口） | 由实例锁与"下载任务表"避免；引擎层对同一目标文件加文件锁 |

## 6.5 超时与重试

参考实现只有一个 `timeout=30`（requests 的语义是"连接与读取的每段间隔"），
对 1.8 GB 的包来说既可能误杀也可能永远挂着。

本项目的超时分层：

| 超时 | 默认值 | 说明 |
|---|---|---|
| 连接超时 | 10 秒 | TCP 建连 |
| 首字节超时 | 30 秒 | 建连后等待第一个字节；镜像慢或不可用会在这里暴露 |
| 空闲超时 | 60 秒 | 两次收到数据之间的最大间隔；小水管的低速下载也不会被误杀 |
| 整体超时 | 不设 | 大文件下载不设总时限（否则大包必然失败），只靠空闲超时兜底 |
| 清单请求超时 | 15 秒 | 小文件，可以严格 |

重试策略：

| 错误类型 | 重试 | 退避 |
|---|---|---|
| 连接失败 / 超时 | 是，最多 3 次 | 1s → 2s → 4s（带随机抖动，避免全校同一时刻重试） |
| 5xx | 是，最多 3 次 | 同上 |
| 404 / 410 | 不重试，报告"资源不存在" | 触发一次清单刷新（上游可能已变更） |
| 403 | 在有防盗链头的情况下重试 1 次（补 `Referer`）；仍失败则报告 | —— |
| 校验和不符 | 是，最多 2 次（从头重下） | 立即重试（可能是传输损坏） |
| 磁盘写入失败 | 不重试 | 报告磁盘问题 |

**每次重试都要换镜像**（若有多镜像），因为失败往往是特定镜像/线路的问题。

## 6.6 代理支持

| 来源 | 优先级 | 说明 |
|---|---|---|
| 用户在 EnvReady 设置里显式填写的代理 | 1 | 最可靠，界面里必须提供 |
| 环境变量 `HTTPS_PROXY` / `HTTP_PROXY` / `ALL_PROXY` | 2 | 尊重系统既有配置 |
| 系统代理（Windows 注册表 `Internet Settings`；macOS `scutil --proxy`） | 3 | 尽量自动读取 |
| 无代理 | 4 | 默认 |

**明确不支持**：PAC 脚本解析（成本高、收益低）。
若检测到系统配置了 PAC，在设置页提示"检测到你的网络使用自动配置脚本，
如果下载失败请手动填写代理地址"。

代理认证：支持 `http://user:pass@host:port` 形式；**日志与诊断包中必须脱敏**。

## 6.7 并发、分片与限速

| 项 | 决定 | 理由 |
|---|---|---|
| 多文件并发 | 默认 2（清单与组件可同时进行） | 校园网带宽有限，并发过高反而更慢且容易触发限流 |
| 单文件分片并发 | **默认单连接**；仅当"文件 > 64 MB 且服务端声明支持 Range 且用户网络未限速"时启用 2–4 分片 | 分片对校园网 NAT 与上游限流不友好，且实现复杂度与出错面显著增加；首期以单连接 + 续传为主 |
| 后台更新限速 | 程序自身更新包在后台下载时限速（默认 1 MB/s，可关） | 不抢占学生正在下载组件或正常上网的带宽 |
| 网速显示 | 实时速度 + 平均速度 + 剩余时间 | 参考项目的经验：学生对"卡住了还是在动"极其敏感 |

## 6.8 进度与取消

- 进度信息统一为：`已下载 / 总大小`、`百分比`、`实时速度`、`平均速度`、`剩余时间`、`当前镜像`。
- **总大小未知时**（服务端未给 `Content-Length`）：显示已下载量 + 不确定进度条，
  绝不显示一个假的百分比。
- **解压阶段也要有进度**（大包解压可能数十秒），并明确文案区分"正在下载"与"正在解压"
  ——参考实现让学生在"进度条 100% 但界面卡住"的状态里等待，体验上等同于卡死。
- 取消语义：
  - 下载中取消 → 保留 `.part` 与 `.meta`（下次可续传），状态回到"未安装"。
  - 解压中取消 → 删除 `.stage-` 目录。
  - 取消后**不留下任何半配置的环境变量**（环境变量只在步骤 7 才写）。
- 取消必须**立即生效**（在数据块边界检查取消标志），不能等到下载完才响应。

## 6.9 校验和计算

- 边下载边流式计算 SHA-256（不要下完再读一遍文件，大文件会多花数十秒）。
- 续传时必须**从头重算**（因为分片拼接后的整体哈希必须从头算）；
  实现上：续传时先读已有分片算一遍哈希，再继续追加计算。
  这会多读一次磁盘，但换来正确的哈希，是值得的。
- 若清单只给了大小没给哈希（首期兜底情况），则**记录为"未校验"**并在界面上标注，
  绝不假装校验过。

## 6.10 面向用户的文案（与 `08` 配合）

| 情况 | 文案 |
|---|---|
| 正常下载 | "正在下载 Python 3.12.10（约 26 MB），已下载 12 MB，约 20 秒后完成" |
| 换镜像 | "当前下载地址较慢，已自动换到更快的地址继续下载" |
| 不支持续传 | "下载服务器不支持断点续传，正在重新开始下载" |
| 签名过期 | "下载地址已过期，正在重新获取" |
| 磁盘空间不足 | "你的 D 盘剩余空间不足，这个环境大约需要 500 MB。请清理后重试，或换一个磁盘。" |
| 网络不可用 | "网络好像不通。请检查网络连接；如果学校网络需要代理，可以在设置里填写。" |
| 校验失败 | "下载的文件不完整（可能是网络中断导致），我们正在重新下载。" |
| 最终失败 | "下载失败了三次，暂时无法完成。你可以稍后重试，或者换用离线安装包。" + [重试] [选择离线包] |

**注意最后一行**：必须始终给用户一条"还能怎么办"的路。参考实现的最终呈现是一句
`下载失败：<HTTP 错误或英文异常>`，等于把问题丢回给不会解决它的人。

## 6.11 离线安装包支持（兜底能力）

即使有自更新与多镜像，仍有"完全没有网络"的场景（机房断外网、考试环境）。
因此保留一条出路：

- 界面上提供"我有离线安装包"入口：用户选择本地文件（或把文件放进指定目录），
  引擎跳过下载、直接进入校验与安装流程。
- 校验仍然执行（哈希可与清单比对；若清单里的版本不同则提示"这个文件与当前版本不匹配，仍要安装吗？"）。
- 该能力同样用于"下载反复失败"的兜底，与 6.10 的最后一行文案配合。
