2026-10-16  议题一：开发语言选型
====================================================================

【想法】第一版推荐：Python + PySide6
（前提假设：项目需要跨届交接，由不同届学生长期维护）

理由：
  1. 与参考实现 murig 同语言，其 4,315 行源码可逐段对照学习，而非"翻译"过来；
  2. 学生团队可维护性最高：语法直白、注释文化好、生态文档多；
  3. 标准库已覆盖 zip / tar.gz / tar.xz、winreg、subprocess、hashlib、urllib，
     一个第三方 GUI 库之外几乎不需要别的依赖 → 依赖越少结构越清楚；
  4. 云端巡检脚本与客户端同语言，一套技能栈维护两半；
  5. Qt 是三平台唯一都成熟的桌面 GUI 方案之一，QSS 足以做出"简洁"的界面；
  6. 前期 Install-MinGW.ps1 验证的是策略与算法（多镜像测速重试、魔术字节校验、
     只写 HKCU、Path 备份/类型保持/广播/回读、可还原），与语言无关，可直接移植。

此方案必须用架构解决的三个弱点：
  1) 自更新：PyInstaller onefile 的 exe 运行时无法替换自身（Windows 文件锁）。
     对策：一开始就用 onedir（目录模式）+ 独立启动器 —— EnvReady.exe 极小且很少改动，
     只负责"检查更新 → 切换 app/<版本>/ 目录 → 拉起主程序"，自更新只换 app/<版本>/。
  2) 体积大 + 杀软误报：对策：onedir 不用 onefile；裁剪无用 Qt 模块；
     首期不做代码签名，自更新走"提示新版本 + 引导官方渠道"降级策略。
  3) .7z 无标准库支持，而 C/C++ 工具链包主要是 .7z。
     对策：沿用前期已实测的三级方案 —— 系统 tar.exe（Win10 1803+ 的 bsdtar 支持 7z）
     → 已装 7-Zip → 内置/下载 7zr.exe。不自己写 7z 解析器。

未选其它语言的理由：
  - Go：体积与自更新最优，但 GUI 生态弱（Fyne 风格自绘不像原生；Wails 需前端 + 依赖 WebView2），
        且当时假设团队上手成本高；
  - Electron / Tauri：UI 能力最强，但 Electron 体积巨大、Tauri 依赖 WebView2，
        等于给"帮新手省事"的工具引入新的失败点；
  - C# / Avalonia：Windows 体验最好，但 macOS/Linux 桌面生态弱，与三平台一致的目标不符；
  - Rust：学习曲线过陡，团队接不住。


【想法】第二版推荐（条件变更：维护一直由我们本团队进行，不跨届交接）
→ 改选：Go

天平倒向 Go 的四个原因：
  1. 自更新从"需要设计一套绕行方案"变成语言的常规操作：
     下载新二进制 → 重命名旧文件 → 写入新文件 → 重启。出错面远小于启动器方案。
  2. 分发体积与第一印象：单文件静态编译约 15–20 MB，对比 Python+Qt 的 100–150 MB；
     机房/宿舍网络下，这是用户能直接感知的差异。且 PyInstaller 产物是杀软误报重灾区，
     "下载即被拦"对零基础用户等于项目失败。
  3. 语言层面预防"静默失败"——直接对应"代码不能混乱、方便后续维护"的要求。
     murig 实测缺陷中有一大类是静默失败，例如：
       · _run_after_extract 的 docstring 明写"失败只告警，不中断流程"（main.py:3020-3045）
       · _configure_env 整体 try/except，失败只往日志写一行（main.py:3144-3174）
       · _load_settings 整体 try/except pass（main.py:4271-4297）
       · FETCHERS.get() 缺项直接 continue，界面上零提示（main.py:4212-4215）
       · after_extract 编译失败后流程照常写环境变量，界面仍可能显示"已配置"
     Go 的 if err != nil 强制面对每个错误，编译期就无法忽略；静态类型 + gofmt
     统一风格，从工具层面消除团队协作的风格分歧与隐性错误。
  4. 交叉编译一条命令出三平台，交付与发版流程简单。

需要接受的代价：
  - 开发速度慢于 Python（尤其 UI 迭代）；
  - GUI 需重新选型：主选 Wails（Go 后端 + HTML/CSS 前端，界面表现力最强、最适合做引导式流程，
    代价是依赖系统 WebView2，需在启动时检测并引导安装，或退化为备用界面）；
    备选 Fyne（纯 Go、零外部依赖，代价是必须内置中文字体否则中文显示为方块，
    且界面定制能力弱、复杂布局代码量大）；
  - 参考实现的现成 Python 实现不能直接照搬，需按设计思路重写。

什么情况下改回 Python：团队对 Go 的投入意愿不足，或希望最快看到可运行原型。


【决定】2026-10-16 定稿：**Go + Wails**，保留 Fyne 作为降级预案。
  - 主选 Wails（Go 后端 + HTML/CSS 前端）：引导式界面表现力最强；风险是依赖系统 WebView2
    → 启动时检测，缺失则静默引导安装（per-user，不需管理员权限），并准备降级界面。
  - 降级预案 Fyne（纯 Go、零外部依赖）：注意必须内置中文字体子集，否则中文显示为方块。
  - 交付形态：单文件静态二进制，`-ldflags "-s -w"`，约 15–20 MB。

2026-10-16  议题二：自更新机制设计
====================================================================

【原理】正在运行的程序无法原子替换自身（Windows 上运行中的 exe 被文件锁；macOS/Linux
  虽可 unlink，但运行中的进程仍指向旧 inode）。因此"替换"这个动作必须交给一个不在
  被替换范围内的角色。一切自更新方案都是这条原理的变体。

【决定】采用「启动器 + 版本目录 + 指针文件」方案（目录版本化），而非「exe 自我改名后覆盖」。
  理由：更新动作退化为"改一个指针文件"——天然原子、天然可回滚、不碰运行中的文件
  （杀软最不敏感）、天然支持多版本共存。

目录结构（Windows 示例，位于用户可写目录）：
  %LOCALAPPDATA%\EnvReady\
    EnvReady.exe                启动器（极小 Go 程序，逻辑稳定、极少变动）
    current                     指针文件，内容为版本号，如 "1.1.0"
    current.bak                 上一版指针（回滚用）
    app\
      1.0.0\EnvReady-main.exe   真正的程序（Wails 产物，前端已 embed 进二进制）
      1.1.0\EnvReady-main.exe
    downloads\                  下载缓存（*.part）
    logs\

关键设计点：
  1. 启动器拉起主程序后【立即退出、不常驻】→ 于是启动器自身也能被安全替换，
     完全不需要任何"自我改名"技巧。这是本方案最关键的一步。
  2. 指针文件原子写：先写 current.tmp，再 rename 覆盖 current。
  3. 新版本先解压到 app\<ver>.tmp-<随机>，校验通过后再原子 rename 为 app\<ver>。
  4. 防变砖：启动器启动新版后，要求新版在 N 秒内写出"启动健康"标记
     （在主窗口 ready 事件后写入）；未写出则杀掉子进程并把 current 回退到上一版本，
     并且下次启动时用自然语言告诉用户"新版本启动失败，已自动回到上一个可用版本"。
     健康检查只对刚更新的版本执行，避免每次启动都等待。
  5. 绝不打断进行中的任务：新版本在后台静默下载、校验、就位；仅在"当前无部署任务"时
     提示"重启后生效"，用户可选"稍后"，且"稍后"也保证下次启动自动用新版。
  6. 单实例锁（Windows named mutex / Unix lock file）：防止学生双击两次造成两个实例同时写更新。
  7. 启动器自愈：current 缺失/损坏/指向不存在的目录时，扫描 app\ 选可用版本；
     全部不可用时引导下载完整安装包。
  8. 更新下载复用我们给用户写的那套下载引擎（断点续传、哈希校验、多镜像测速择优、代理）
     —— 自更新是我们自己下载引擎的第一个使用者。校网直连 GitHub 常失败，镜像不是可选项。
  9. 校验：清单提供 SHA-256；更进一步用签名（minisign/cosign，公钥硬编码进客户端）。
     首期 SHA-256 + HTTPS 只能防传输损坏与镜像投毒，不能防仓库被入侵——如实记录，不假装安全。
 10. 包格式：macOS 的 .app 不能用 zip（丢符号链接与权限位），用 tar.gz 或 ditto。
     包内含文件清单与逐文件哈希，解压后逐项校验（专门防 murig 那种"解压不完整但静默通过"）。
 11. 不要用 UPX 压缩：省一点体积，但杀软误报率显著上升，对零基础用户得不偿失。
 12. 版本检测不走 GitHub API（未认证限流 60 次/小时，机房 NAT 下全体学生共用出口 IP 必然 403），
     改用自己的静态清单 JSON + CDN（jsDelivr / raw），无限流。
 13. 更新说明写人话（"修复了下载中断后必须从头开始的问题"），不要贴 commit 列表。

【想法】三层"更新"必须分开，不能混为一谈：
  - 客户端二进制：低频、需重启（本议题讨论的就是它）
  - 资源清单 JSON：高频、无需重启、自动生效
  - 组件版本：用户主动选择，与更新无关
  → 教训来自 murig：它把 29 个组件的知识硬编码在 build_components() 中，
    导致新增一个组件必须改代码并重新发版。我们绝不能把清单编进二进制。

【想法】不以现成自更新库（go-selfupdate / minio-selfupdate 等）为主方案：它们多是
  "重命名自身 + 替换 + 重启"，不覆盖我们要的"目录版本化 + 启动健康检查 + 自动回退 +
  用户可写目录"。可借鉴其原子替换工具函数，但主流程自己实现（启动器仅几十行）。

【待办】确定安装目录规范与首次安装的落地方式（安装包 vs 绿色免安装）。
【待办】确定清单 JSON 的存放位置与签名方案（首期 SHA-256，后续签名）。
【待办】Python + PySide6 方案已归档为历史备选（见议题一），若 Go 路线受阻可回退。

2026-10-16  议题二·拆分：目录版本化 与 启动健康检查 的具体约定
====================================================================

【修正】上一轮同时说了"启动器拉起主程序后立即退出"和"启动器做启动健康检查"，
  这两条互相矛盾——启动器退出了就没人判定健康。修正为：
  **启动器是否驻留，由指针文件里的 state 决定。**
    state = stable  → 拉起主程序后立即退出（99% 的启动路径）
    state = pending → 驻留最多 N 秒观察健康标记，判定成功则置回 stable，失败则回退

【修正】指针文件由纯文本升级为 JSON（回退需要知道上一个版本、是否待确认、试过几次）：
  current.json = { schema, version, state: stable|pending|broken, prev, attempts, nonce, updated_at }
  写入始终原子：current.json.tmp → rename。

【决定】健康标记的传递机制：**文件 + nonce**。
  比"退出码"强（能表达"起来了但白屏"），比"管道"简单（启动器退出后管道会断，
  Windows 跨进程句柄传递麻烦）。nonce 由启动器生成、经环境变量 ENVREADY_HANDSHAKE 传给子进程，
  用于识别陈旧标记。

【决定】两阶段健康标记（诊断价值）：
  stage 1 = Go 侧 OnStartup 写入（进程活着 + WebView2 初始化成功）
  stage 2 = 前端 DOM ready 后回调 Go 写入（前端资源加载并执行成功）
  **只有 stage 2 算成功**；但两阶段分开记录，能让日志区分"WebView2 挂了"与"前端挂了"。

【决定】健康检查超时 N 暂定 30 秒（老机房机器 + WebView2 冷启动留余量，且只发生在
  刚更新后的第一次启动）。区分两种情况：进程秒退/退出码非 0 → 立即失败；
  进程活着但超时 → 记一次尝试，attempts < 2 再给一次机会，达上限才回退。

【决定】回退动作：current.json 改回 {version: prev, state: stable}；
  失败版本目录改名为 <ver>.broken-<时间戳>（不删除，保留证据）；
  并以自然语言告知用户"新版本启动失败，已自动回到上一个可用版本"+ 查看详情入口。

【决定】程序自身目录与组件安装目录必须分开：
  程序自身 <APP_ROOT>（随客户端更新切换）；组件环境 <ENV_ROOT>（用户资产，
  **绝不随客户端更新而重装或清理**）。三平台 APP_ROOT：
  Windows %LOCALAPPDATA%\EnvReady\ ／ macOS ~/Library/Application Support/EnvReady/ ／
  Linux ~/.local/share/envready/。

【决定】版本目录保留策略：当前版本 + 最近 2 个历史版本 + 1 个 broken 样本；
  超出部分在**启动成功后**后台清理（不在启动前清理，避免阻塞启动）；清理失败只记日志。
  <ENV_ROOT> 永不清理。

【决定】两把锁，粒度不同：实例锁（防双击开两个，Windows named mutex / Unix flock）
  与写入锁（只在写 current.json、替换启动器时短暂持有）。锁文件记 PID + 时间戳，
  PID 不存在或超时视为陈旧锁并接管。

【待办】崩溃恢复矩阵需在实现前逐条写成测试用例（下载中断点、校验失败、解压中断、
  rename 前后、指针切换前后、pending 观察中崩溃、回退中崩溃、启动器替换中断、
  启动器自身损坏）。详见对话中的矩阵表。


--------------------------------------------------------------------
清单 JSON 的具体约定
--------------------------------------------------------------------

【决定】清单分成三类，职责与频率分离：
  client.json             客户端自身版本与包      低频（发版才变）  启动后延迟 5s，24h 最多一次
  components/index.json   组件目录（画卡片用）    中频             启动后延迟 1s，带 ETag
  components/<key>.json   单组件版本与地址        高频             用户点开该组件时懒加载

【理由】实测单组件版本数差异极大（node 289、tomcat 202、python 166、maven 46、
  dameng 1）。合并成大清单会导致每次全量下载解析；分片后首屏只拉几 KB 的索引，
  巡检 CI 也只改动受影响的那一个文件，diff 干净。

【决定】client.json 字段：schema / channel / latest / min_supported / published_at /
  notes（按语言给人话，不用 commit 列表）/ mirrors（前缀列表，多镜像复用一个包）/
  packages（按 windows-amd64、windows-arm64、darwin-arm64、darwin-amd64、linux-amd64 分）/
  launcher（启动器单独版本，与主程序解耦）/ signature。
  min_supported：低于它的客户端强制更新（用于安全修复）。

【决定】components/<key>.json 关键字段及设计动机：
  install_kind  区分 归档/安装器(静默参数)/npm/便携单文件 —— murig 用一串布尔字段拼，易漏
  platforms     按 windows-arm64 粒度建模 —— murig 实测 5 个组件在部分平台无包却零提示
  post_notes    必须渲染到卡片上 —— murig 定义了也渲染了，但只打进日志窗的 warn 行，小白看不到
  requires      依赖建模 —— murig 完全没建模（Claude Code 需先装 Node，只在 README 说了）
  verify        "装完自己验一遍" —— 相对 murig 的核心差异（它只把进度条跑到 100% 就算成功）
  mirrors + sha256  实测 218 条直链 26 条异常、两个 Python 版本真 404，必须有兜底与校验
  headers       防盗链 —— 实测某信创数据库 OSS 必须带 Referer
  archive.strip_root  解压是否去顶层目录 —— murig 用"只有一个子目录就进去"的启发式，不够明确
  size / released_at  界面显示"多大、什么时候发的"，让新手有判断依据
  schema        客户端遇到未知版本要降级而非崩溃

【决定】清单体积控制：versions 只放"推荐版本 + 最近 8 个"，另给 versions_all_url 供高级用户；
  目标单组件清单 < 50 KB、索引 < 30 KB。

【决定】信任根链条必须写进文档：
  硬编码公钥 → 验签 清单 → 校验 包 sha256 → 校验 解压后逐文件哈希 → 实测自检 verify 命令。
  首期无签名，仅 HTTPS + 哈希，**明确记录为降级状态**；第二期用 minisign 签清单。
  签清单比签包更重要——清单是信任根，改了清单就能把下载指向任意 URL。

【决定】缓存/离线策略：正常带 ETag（304 用本地缓存）；网络失败但有缓存 → 用缓存并标注
  "清单为 x 小时前的快照"；网络失败且无缓存 → 用 embed 进二进制的**出厂快照**并明确标注
  "当前离线，正在使用出厂列表，组件版本可能不是最新"。**与 murig 的关键区别**：它的兜底
  列表过期后静默使用、零提示（实测 jdk 内置 21 而在线 27、node 20.15.0 vs 26.12.0）。

【决定】schema 演进：客户端遇到不认识的 schema 要降级而非崩溃；服务端同时保留旧版清单
  一段时间给旧客户端迁移窗口；客户端可选匿名上报自身版本，用于决定何时停止兼容。

【待办】以下需拍板或实测：
  1) 健康检查超时 N 的最终取值（需在最差机房机器上实测 WebView2 冷启动 + 杀软扫描耗时）；
  2) <ENV_ROOT> 组件安装目录放哪、是否允许用户迁移（迁移会让已写环境变量指向旧路径，
     这是 murig 的坑）；
  3) 是否开放 beta 通道（channel 字段已留，成本低，建议留字段但不开放）；
  4) 签名工具选型（倾向 minisign，跨平台且 Go 库成熟）；
  5) 启动器是否随主程序包一起发布（它极少变，可由主程序在启动器不运行时替换）。

议题三：方案拆分落盘为设计文档（目录：设计文档\）
【决定】把方案拆分到"已经足够详细"，全部写成 15 份文档落盘，不再只留在聊天里：
  00-总览与设计原则.md          设计原则（可解释/可回滚/无静默失败/绝不弄坏电脑）、
                                与 murig 的差异表、术语表、明确"不做"的事
  01-工程结构与代码规范.md      分包职责、注释三类规范（文件头/符号/流程）、
                                错误处理、日志、CI 门禁、红线清单
  02-目录布局与状态机.md        APP_ROOT 与 ENV_ROOT 分离、指针状态机、
                                13 行崩溃恢复矩阵、GC、锁
  03-更新机制.md                启动器与健康检查（nonce + 两阶段）、三层更新分离、
                                回退、12 项测试矩阵
  04-资源清单规范.md            client.json / index.json / 分片；每个字段为什么存在
  05-组件模型与安装引擎.md      安装方式分支、格式矩阵、8 步流水线、verify 自检
  06-下载引擎.md                多镜像测速、续传、分层超时、代理、进度与取消
  07-环境变量管理.md            Windows 注册表协议、Unix shell 协议、版本切换、
                                备份与意图记录、还原、卸载
  08-面向新手的交互与文案规范.md 5 步主流程、术语→人话映射表、说明模板、
                                授权询问、结果页、文案写作规范
  09-C-C++（MinGW）接入.md      前期脚本能力逐条继承清单、发行选择、VS Code 四文件
  10-云端资源仓库与巡检.md      仓库划分、生成流水线、复核门禁、防抖动
  11-安全与信任模型.md          10 条威胁、信任根链条、来源白名单、子进程安全
  12-日志、诊断与支持.md        操作记录（给人看）与诊断日志（给机器看）、脱敏、诊断包
  13-测试与验收.md              分层测试、故障注入、环境变量专项、成功率度量
  14-里程碑与任务拆分.md        S0–S6 阶段、任务清单、风险登记册

【决定】相对议题二新增的关键定论：
  1) 代码组织：按职责分包（cmd/internal/frontend/tools），main 只做装配；
     注释分三类，且"失败会怎样/有没有副作用"是必写项；禁止 _ = err，CI 用 errcheck 拦。
  2) 首期组件范围收窄：只做 C/C++、Python、Java、Node、VS Code 五类；
     数据库、大数据全家桶、AI CLI 全部不做（体积大、需初始化、需基础）。
  3) 组件准入规则：不收录"需要用户机器上已有编译器"的组件——
     murig 让学生 make 编译 Redis/PostgreSQL 是设计缺陷，我们直接不收录。
  4) verify 自检强制：每个组件必须实际跑命令核对版本；进度条 100% 不等于成功。
  5) 不写自造环境变量：只写上游官方要求的变量（MinGW 只加 PATH，不设 MINGW_HOME）。
  6) 来源白名单写死在代码里，不能放清单——无签名阶段清单本身不可信。
  7) 子进程安全：不用 shell 拼接、命令限制在该组件安装目录内、参数禁元字符。
  8) 巡检频率：核心组件每 6 小时（保证 24 小时指标有 4 倍余量）。
  9) 校验和按体积分级；超过阈值只能拿上游公布的哈希，拿不到就在界面上显示"未校验"。
 10) 环境变量：按组件归组的幂等块 + 版本切换整条替换 + 意图记录 + 一键还原。
 11) fish 必须单独处理：把 bash 语法写进 config.fish 会弄坏用户的 shell。
 12) macOS 不能只信 $SHELL（从 Finder 启动时为空）→ 先用账号数据库确定登录 shell。
 13) 首期不提权、不写 HKLM、不写系统目录。
 14) 日志分两类：操作记录（面向学生，人话，"我做过什么"页面）与诊断日志（结构化、脱敏）。
 15) 交付顺序 S0→S6，先命令行后图形：命令行跑通才说明内核正确。
